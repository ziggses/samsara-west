# 战斗内核 v1

战斗内核 v1 是「一场仗能从头跑到尾」的那一层：行动队列、意图预告、目标结算、护体/破防、
状态与冷却、换位、胜负判定、事件播报。它不画界面、不读 CSV、不掷全局随机数——
这些分别由 `UI/`、`Data/` 与注入的随机流负责。

本文回答两个问题：**契约是什么**，以及**哪些还没做**。第 11 节的【遗留清单】就是代码注释里
反复引用的那一份（`BattleTypes.cs`、`BattleUnit.cs`、`BattleFormation.cs`、`BattleModule.cs` 里
共 4 处写着「见 Docs/战斗内核-v1.md 的遗留清单」）。

- 代码：`Assets/_Project/Battle/Runtime/`（`BattleConfig.cs`、`DamageCalculator.cs` 是更早交付的纯函数与配置，不在本文范围）
- 断言：`Tests/EditMode/BattleSessionTests.cs`、`BattleBreakAndStatusTests.cs`、`BattleRunTests.cs`，
  以及构场工具 `BattleLab.cs`
- 数值口径：`Docs/战斗数值-v1.md`（公式、五行、暴击、护体上限、行动值口径）。**本文不重复公式**，
  只讲流程与不变量
- 相关决策：`Docs/架构决策.md` ADR-016（战斗数学是纯函数）

当前状态：内核可用、可复现，EditMode 331/331、PlayMode 15/15 全绿；**尚未接进游戏流程**
（`Flow.GameBootstrap` 没有安装 Battle 模块，见第 9 节）。

## 1. 一场战斗的生命周期

一场战斗 = 一个 `BattleSession` 实例，不跨场复用。

```
BattleSession(BattleConfig config, IDefinitionRegistry registry, IRandomStream battleStream,
              BattleSetup setup, IEventBus eventBus = null)
```

构造时：`setup.Validate` 不合法就抛（「入场清单不合法」），然后按 `BattleSetup` 的 `Party`／`Enemies`
蓝图逐格建 `BattleUnit`（`RuntimeId` 从 **0** 起、按「我方在前、敌方在后」的顺序发），
任一侧一个单位都建不出来也抛（数据没导入时就是这样暴露的），再 `ActionQueue.Reset` 排出初始出手序，
最后播报 `BattleStartedEvent`。

| 成员 | 说明 |
|---|---|
| `Outcome` | `Ongoing` / `PlayerVictory` / `PlayerDefeat` |
| `Phase` | 当前单位的回合阶段，见 1.3 |
| `CurrentActor` | 当前行动者，没在推进时为 `null` |
| `RoundNumber` | 派生值，不单独存储，见第 3 节 |
| `ActionCount` | 已经开始的单位回合数（每 `BeginNextTurn` 成功一次 +1） |
| `Units` / `PlayerUnits` / `EnemyUnits` | 只读列表，顺序稳定 |
| `EnemyIntents` | 预告窗口内的敌方意图，见第 4 节 |
| `GetIntent(runtimeId)` | 单个单位（任意阵营）的计划，**不受预告窗口限制** |

指令入口只有 5 个：`BeginNextTurn()`、`UseSkill(skillId, primaryTargetRuntimeId = -1)`、
`MoveTo(FormationSlot)`、`SwapWith(allyRuntimeId)`、`EndTurn()`（外加原型用的 `RunToEnd(maxActions = 512)`）。
它们都返回 `BattleActionResult`（`EndTurn`/`BeginNextTurn` 除外），被拒绝时带上
`BattleCommandRejection` 枚举——**内核里不允许出现面向玩家的文案**，界面按枚举查文本键。

### 1.1 推进一手：`BeginNextTurn()` 的顺序

1. 战斗已结束（`Outcome != Ongoing`）→ 返回 `null`。
2. 上一手没`EndTurn`（`Phase` 是 `MainAction`／`MoveOrSwap`）→ 记一条警告日志并返回 `null`，**不**偷偷替玩家结束回合。
3. `_queue.PeekNext()` 取最小行动值的单位；一个都没有 → 先 `ResolveOutcome` 再返回 `null`。
4. 置 `CurrentActor`，清 `_mainActionUsed`／`_moveUsed`，`ActionCount++`，播报 `BattleTurnStartedEvent`。
5. **被控住的单位**：`IsActionPrevented` 为真 → 播报 `BattleTurnSkippedEvent`（带造成跳过的
   `StatusId`）→ 直接走 `FinishTurn` → 返回该单位。**整手跳过，但不是没有回合**：
   状态计时、行动值累加照常进行。
6. **敌方单位**：立刻用规划器代打（`ExecutePlannedTurn`）→ `FinishTurn` → 返回该单位。
   敌方回合不需要外部指令，这是「一手」对玩家而言就是 `BeginNextTurn` + `EndTurn` 的原因。
7. 我方单位：`Phase = MainAction`，返回给调用方等待指令。

返回 `null` 与「返回了一个单位但 `Phase == Finished`」是两种不同的情况，调用方都要处理。

### 1.2 结束一手：`FinishTurn()` 的顺序

顺序有语义，不要调换：

1. `TickCooldowns()` —— 递减所有冷却（见第 6 节）。
2. `TickStatuses()` —— 递减状态时长、结算每回合生命增减，把到期的挑进临时表，逐个播报
   `BattleStatusExpiredEvent`。
3. `TickBrokenTurn()` —— 破防计时（见第 5 节）；到期则播报 `BattleBreakRecoveredEvent`。
4. **只在「被自己的持续伤害打死」时**在这里播报 `BattleUnitDiedEvent`：被技能打死的那次已经在
   技能结算里播过了，同一个死亡不允许报两次。
5. `TurnsTaken++`，`_queue.Advance(actor)` 把行动值推进到下一手，播报 `BattleTurnEndedEvent`
   （带上推进后的 `ActionValue`）。
6. 清回合内标记、`_plansDirty = true`（下一手的意图要重算）、`Phase = Finished`。
7. `ResolveOutcome()`。

### 1.3 `TurnPhase` 状态机

| 值 | 含义 | 能做的指令 |
|---|---|---|
| `Idle` | 还没推进，或已经结束 | `BeginNextTurn` |
| `MainAction` | 待主行动，也可以先移动／换位 | `UseSkill` / `MoveTo` / `SwapWith` / `EndTurn` |
| `MoveOrSwap` | 主行动已用，只剩一次移动／换位（可放弃） | `MoveTo` / `SwapWith` / `EndTurn` |
| `Finished` | 该单位回合结束，等下一手 | `BeginNextTurn` |

主行动与移动是**两个独立的额度**，主行动用掉后仍可换位一次；`MoveTo`／`SwapWith` 各只能用一次
（`MoveAlreadyUsed`）。

## 2. 行动队列（ATB）

`ActionQueue` 是 `internal` 的，外面只能通过 `BattleSession` 观察结果。

- **初值**：`max(1, round(10000 / clamp(speed, 1, 999)))`，值越小越先手。速度 30 → 333，速度 5 → 2000。
- **出手后是「累加间隔」而不是「重置」**：`ActionValue += 间隔`。所以速度 40（间隔 250）的单位
  会在 250、500、750 连续出手，速度 14（间隔 714）的单位插进第三手。这一条决定「快者到底能连动几下」，
  改它等于改全部手感——测试 `速度决定行动值_快者在自己第二个回合之前不会被超车` 就是钉这个算术的。
- **平局判据**：行动值相同时按 `FormationIndex` 升序。它是**全局建队序号**：建队时我方在前、敌方在后
  连续编号，于是我方 0/1/2、敌方 3/4/5，同速时我方先动。整场战斗恒定。
- ⚠️ **`FormationIndex` 与 `Slot` 是两个东西，不要互相替代**：
  `FormationIndex` 是建队序号（整场不变，用于破平局与命中集合排序）；
  `Slot`（`FormationSlot`，列 0–2 × 排 0–1）是**当前站位**，换位会改写它，
  技能的列／排命中范围跟着它变。
- **归一化**：当全体最小行动值 ≥ `1_000_000` 时，统一减去该最小值。这是**正确性保险而不是性能优化**——
  长局不让 `int` 溢出；减掉同一个数不改变任何相对次序。
- `PreviewOrder(n)` / `PeekNext()` 只是读，不改状态；`Advance(unit)` 才推进。

## 3. 回合数（`RoundNumber`）

`RoundNumber` 是派生值：`1 + min(存活我方单位的 TurnsTaken)`，没有存活我方单位时返回 0。
**不是**「第几个行动」，也不依赖 `ActionCount`。用它的地方（界面第几回合、按回合判定的未来规则）
要接受「敌方连动不会让回合数前进」这个定义。

## 4. 意图预告

- `EnemyIntents`：取 `PreviewOrder(Config.IntentPreviewLead)` 的前若干格，**只留敌方**，逐格给
  `BattleIntent`；该单位没有计划时给 `BattleIntent.None`。`IntentPreviewLead = 0` 时恒为空列表。
  意思是「接下来 `IntentPreviewLead` 个行动者里，敌方要做什么」。
- ⚠️ `EnemyIntents` 返回的是**内部复用列表**，下次读取就被覆盖，要留存必须自己复制一份。
  界面每帧读它没问题，把它存进字段就是等着踩坑。
- `GetIntent(runtimeId)`：直接问某个单位的计划，**不受窗口限制**，用于调试与界面点选。
  两者共用同一份计划缓存，不会产生不一致。
- **规划是纯函数**：重算计划**不消耗随机数**。随机目标（`TargetIsRandom`）在**执行时**才掷。
  否则「打开界面看一眼」会改变战斗结果。
- 选招顺序（`BattleActionPlanner`）：先挑能造成最高确定伤害的技能 → 没有伤害技能就挑治疗量最高的
  → 都没有就取第一个可用技能。灵力不够、冷却中、没有合法目标的技能直接跳过。
- 选目标（`ChoosePrimaryForAi`）：敌对目标取**当前生命最高**的，友方目标取**当前生命比例最低**的，
  同分按 `FormationIndex`。随机技能改由执行时抽签（`Pick`）。
- **被控住（`preventsAction`）的单位一律返回 `BattleIntent.None`**：已经动不了的单位不该再给预告。
- 技能的命中集合一律按 `FormationIndex` 升序返回，这个顺序就是「多段技能逐段掷骰」的顺序——
  它必须确定，否则同一个种子也重放不出同一场。
- 计划缓存在 `_plans` 里，`_plansDirty` 在任何会改变战场的事情之后置真（回合结束、状态变化、
  单位死亡、换位等），下次查询时整批重算。

## 5. 破防与状态

### 5.1 护体值与破防

- 每个单位有 `BreakValue`／`BreakThreshold`（上限），进场时护体满值。
- `ApplyBreakDamage` 削护体；削到 0 时**进入破防**：`IsBroken = true`，
  `BrokenTurnsRemaining = Config.BrokenDurationTurns`，播报 `BattleBrokenEvent`。
- **破防期间不能再削**：`ApplyBreakDamage` 直接返回 false，技能结算里的 `BreakDamage` 记为 0。
- **计时按「被打者自己的回合」**：`TickBrokenTurn()` 只在**该单位自己**的回合结束时递减。
  也就是说，一个比我方慢很多的敌人，破防窗口不会因为「我方连打三手」就流逝——
  它在自己的回合里结算。到期时恢复：`IsBroken = false`、`BreakValue` **重置为上限**，
  返回 true 让 `FinishTurn` 播报 `BattleBreakRecoveredEvent`，一次恢复只报一次。
- 破防期间的增伤倍数与附加伤害口径见 `Docs/战斗数值-v1.md` 第 3 节，本文不重复。

### 5.2 状态（`BattleStatusInstance`）

- 实例只有三项：`StatusId`、`RemainingTurns`、`Stacks`；效果取自 `StatusDefinition`。
- 叠加规则：

| `StackRule` | 已有同类状态时 |
|---|---|
| `Refresh` | 不叠层，把时长重置为定义里的最大值 |
| `Stackable` | 层数 +1（上限 `MaxStacks`），时长按新层刷新 |
| `StrongestOnly` | 只保留「更强」的那一份，并刷新时长 |

- 结算时机：**在状态所在单位自己的回合结束时**递减。递减前先算这一回合的效果，
  所以 `durationTurns: 1` 的眩晕能实打实控住它一整个回合。
- 每回合生命增减（`HealthDeltaPerTurn`）与递减在同一处结算；因持续伤害而死会在这里播报
  `BattleUnitDiedEvent`（见 1.2 第 4 步的防重复）。
- `preventsAction` 的语义是**跳过整个回合**，不是「不能打主行动」：`BeginNextTurn` 直接就
  `BattleTurnSkippedEvent` + `FinishTurn`，玩家没有任何指令窗口。

## 6. 冷却

- 冷却按**自己的回合**递减（在 `FinishTurn` 里，先于状态结算）。
- 记录「本回合用过的技能」的集合 `_cooledThisTurn`：技能刚放出的那一手**不递减**。
  否则冷却 2 的技能会在放出的同一手就掉到 1，等于凭空少一回合。
- ⚠️ **已知坑（已修，不要再踩）**：`TickCooldowns` 里不能一边 `foreach` 遍历
  `Dictionary` 一边用索引器给它赋值——即使键已存在，索引器赋值也会推进内部版本号，
  当场抛 `InvalidOperationException: Collection was modified`。
  现在先把键抄进临时表再改值。这个坑只在「冷却跨过一手」时才踩得到，所以用例必须真的走过两个冷却回合，
  只在同一手内查冷却的用例是照不出来的。

## 7. 随机与可复现

- 内核**只接收一条**注入的随机流（构造参数 `battleStream`），不自己去拿全局随机数。
  生产侧由 `BattleModule` 用 `RandomStreams` 的具名流 `battle` 派生，同一个种子 → 同一场战斗。
- 用随机数的地方只有：命中的概率判定、暴击、随机目标抽签、逐段伤害的浮动。查询意图与预览出手序都不掷。
- 换位、移动、状态结算都**不含随机**，所以「读一眼预告再决定」不会改变随机序列。

## 8. 事件

全部挂在 `BattleEventChannel.Channel`（= `EventChannel.Battle`）上，都是只读 `struct`：

| 事件 | 时机 | 关键字段 |
|---|---|---|
| `BattleStartedEvent` | 构造函数末尾 | `EncounterId`、`PlayerCount`、`EnemyCount`、`IsBoss` |
| `BattleTurnStartedEvent` | 每次 `BeginNextTurn` 选定行动者后 | `RuntimeId`、`Side`、`ActionValue` |
| `BattleTurnSkippedEvent` | 被控住跳过整手时 | `RuntimeId`、`Side`、`StatusId`（造成跳过的那个状态） |
| `BattleTurnEndedEvent` | 回合结束、行动值推进后 | `ActionValue`（推进后的值） |
| `BattleDamagedEvent` | 每次伤害结算 | `Damage`、`IsCritical`、`HealthAfter`、`ElementRelation` |
| `BattleHealedEvent` | 每次治疗结算 | 治疗量、剩余生命 |
| `BattleBrokenEvent` | 护体被削到 0、进入破防 | `RuntimeId`、`Side` |
| `BattleBreakRecoveredEvent` | 破防到期、护体重置 | `RuntimeId`、`Side`、重置后的 `BreakValue` |
| `BattleStatusAppliedEvent` | 状态挂上／叠层 | 状态 ID、剩余时长、层数 |
| `BattleStatusExpiredEvent` | 状态时长归零被移除 | `StatusId` |
| `BattleUnitDiedEvent` | 单位死亡（技能致死或持续伤害致死，各只报一次） | `RuntimeId`、`Side`、`KillerSkillId`（持续伤害致死时为空） |
| `BattleSwappedEvent` | 换位或移动到空位 | `RuntimeIdA`／`RuntimeIdB`、`SlotA`／`SlotB` |
| `BattleEndedEvent` | 胜负判定 | `Outcome`、`Rounds`、`ActionCount` |

所有事件只带 ID、枚举与数值快照，**不带 `BattleUnit` 引用**：界面在回调里拿到的是「那一刻」，
不是还在变的活对象，否则飘字会跟着后续伤害一起跳。

事件是**给界面与战斗日志看的**：内核自己的状态不由事件驱动，测试断言事件数量时要注意
「一次恢复只报一次」「一次死亡只报一次」这类约定。

## 9. 装配（`BattleModule`）

- `BattleModule.Install(IServiceRegistry, BattleConfig)` 把战斗服务注册进服务定位器，对外暴露
  `IBattleService`：`Config`、`Current`（当前这场，没有就是 `null`）、`HasActiveBattle`、
  `StartBattle(setup)`、`EndBattle()`。**服务只管「开一场 / 记住当前这场」**，`BattleSession` 本身
  不做成服务——一场战斗是有始有终的产物，而服务是跨场景存活的。
- **尚未接线**：`Flow.GameBootstrap` 目前没有安装 Battle 模块，也没有「探索遇敌 → 进战斗」的入口。
  因此 PlayMode 里断言「已安装模块列表」的用例仍然只覆盖启动装配，**不要以为战斗已经能进游戏了**。

## 10. 测试怎么用（`BattleLab`）

`BattleLab` 是 EditMode 的构场工具：`Character`／`Enemy`／`AttackSkill`／`StatusSkill`／`Status`
造定义，`Config()` 造配置，`Bus()` 造事件总线，`SetPrivate(obj, "_field", value)` 改私有字段。
它内部用 `ScriptableObject.CreateInstance` 造定义资产，`Dispose` 时统一 `DestroyImmediate`。

用 `BattleLab` 时的两个陷阱：

1. **`Status` 的修正量默认值分两组**：攻／防／速是加算进 `1 + modifier` 的（中性值 **0**），
   `incomingDamageModifier`／`breakDamageModifier` 是乘区（中性值 **1**）。默认值给错会造出
   「什么都不写就 +100% 攻防」或者「承伤 0 倍」的假状态。（资产默认值是 0，只有 CSV 会写成 1。）
2. **速度决定「第几手」**：行动值是累加的间隔，`speed: 5` 的单位在这类用例里往往一手都轮不到。
   写「我打一下、然后敌人行动」这种序列时，让双方同速（同速按布阵我方先手）最省事。

## 11. 遗留清单

### 11.1 需要拍板（有缺口，但还没有口径）

没有口径就不写代码——骨架期的规矩是「宁可缺口，不留走不通的分支」。

| # | 现状 | 缺什么 / 要拍什么 | 出处 |
|---|---|---|---|
| 1 | `BattleOutcome` 只有 `Ongoing`／`PlayerVictory`／`PlayerDefeat` | **逃跑与剧情撤退没有口径**（成功率的判据、逃跑失败是否白挨一下、剧情强制撤退算不算失败） | `BattleTypes.cs` 的 `BattleOutcome` 注释 |
| 2 | `BattleActionKind` 只有 `Skill`／`Swap`／`EndTurn` | **道具、防御、逃跑、联合技都没有口径**。代码里**刻意不预留**占位枚举值，避免出现永远走不通的分支。任务书里列了这四类，落地前先补口径 | `BattleTypes.cs` 的 `BattleActionKind` 注释 |
| 3 | 列／排技能判断「打敌还是打友」用的是 `Power > 0` 的**临时判据** | 技能表要补一个显式字段（例如 `hostileOnly`），否则「0 威力的列攻」「对列治疗」这类技能会被归错阵营 | `BattleTargeting.cs` 的 `RequiresHostilePrimary` |
| 4 | 落位按**建队顺序**算：每侧前三个进前排、从左到右（`BattleFormation.SlotForIndex`），`encounters.csv` 的 `formation` 列**不参与**落位；敌人超过 6 个只记错误日志并丢弃多余的 | `encounters.csv` 的表头说 `formation` 只是策划备注用的标签，而 `EncounterDefinition.Formation` 字段的注释写的是「例如 1,1;2,1;3,2（列,行）」——两处对不上。要么改注释，要么真的实现它 | `BattleFormation.cs` 的 `BattleFormation` 注释；`BattleSetup.cs` 的 `BattleFactory.FromEncounter` |
| 5 | 治疗只读 `HealPower`，**完全不看五行** | 相生用于治疗／增益加成仍未做（`ElementRules` 的关系表已经备好）。数值文档第 2 节与第 7.4 节都登记了这条，两处要同时划掉 | `Docs/战斗数值-v1.md` 第 7.4 节 |
| 6 | `RunToEnd(maxActions = 512)` 会用规划器**代打我方** | 它是原型与测试用的「把这场跑完」，不是玩法也不是 AI。真正的自动战斗／加速播放要另立口径 | `BattleSession.RunToEnd` |
| 7 | 内核不认识 UI，也没有接进流程 | 「探索遇敌 → 进战斗 → 战后结算」的接线在 Flow／Exploration 侧，尚未开始 | `BattleModule.cs` 注释 |
| 8 | 敌方 AI 只有「最高伤害 / 最高治疗 / 第一个可用」三档 | 任务书里的威胁评估、技能连携、集火等都没有口径 | `BattleActionPlanner` |

### 11.2 已定口径的取舍（像 bug，其实是有意的——改之前先看完理由）

| 现象 | 为什么这样定 |
|---|---|
| 换位只改 `Slot`，**`FormationIndex` 不变** | 后者是建队序号，同时是行动值相同时的平局判据与命中集合的排序键。跟着换位走的话，换一次位就会悄悄改掉后续所有同速单位的出手顺序、以及多段技能的掷骰顺序 |
| 出手后行动值是 **累加间隔**，不是重置为初值 | 累加才等于「速度 = 出手频率」：速度 40 的单位出手次数正好是速度 20 的两倍。重置会让快者的收益变成一次性 |
| 破防计时**按被打者自己的回合**递减 | 否则一个慢速敌人会被我方连打几手就「自然」脱离破防，增伤窗口与它的行动次数脱钩 |
| 状态是**先结算效果、再递减时长** | `durationTurns: 1` 的眩晕才能实打实控住它一整个回合，而不是挂上就掉 |
| `RoundNumber` 是「存活我方单位最少行动次数 + 1」 | 它是给界面看「打到第几回合」的，不参与任何规则判定。敌人连动不会让它前进 |
| 敌方回合在 `BeginNextTurn` 里**直接结算完** | 「一手」对玩家就是 `BeginNextTurn` + `EndTurn`，界面不必模拟敌方操作 |

## 12. 改这里的纪律

1. **先让断言变红，再让它变绿**：新增断言必须先证明它能失败，避免「永远绿」的假测试。
   本文档第 6 节的坑、以及「速度决定第几手」的算术，都是这条纪律找出来的。
2. **改行动值模型等于改手感**：累加 / 重置、平局判据、归一化阈值三样一起看，改前先把
   `BattleSessionTests` 的相关用例读一遍。
3. **内核不产出面向玩家的文案**：只给 ID、枚举与事件，文案在 `Localization/`。
4. **数值改在 `BattleConfig`／CSV，不要写进内核**：内核里出现魔法数就是漏了配置项。
5. 已经实现的条目要从本文第 11 节与 `Docs/战斗数值-v1.md` 第 7.4 节**同时**划掉，
   两个清单是同一份待办的两个视角。
