- **结论（2026-09-24）**：以 `BattleConfig.cs` 既定目标为准 —— **常规 4–6 回合、Boss 10–15 回合**；采用《战斗数值 v1》文末**方向一（抬敌人数值，不动角色手感）**。
- **落地动作**：
  - [x] `enemies.csv` 血量与护体重定（首章杂兵 240–350 血 / 护体 30–52；Boss 1400 血 / 护体 120）
        —— **首轮口径，已被第二轮取代**（杂兵 210–305 血 / 护体 90–120；Boss 1400 血 / 护体 180，见 P7 补记）
  - [x] 破防额外伤害口径 `5% → 2%`（`BattleConfig._brokenBonusHealthRatio`）——这是本轮最关键的一处改动，理由见下
  - [x] 新增节奏校算器 `Editor/Tools/EncounterPacingEstimator.cs`（菜单 `SamsaraWest/数据/战斗节奏校算`）
  - [x] 新增断言 `Tests/EditMode/EncounterPacingTests.cs`：常规 4–6 回合、Boss 10–15 回合、单回合不得吃掉 Boss 25% 以上最大生命
  - [x] 同步《战斗数值 v1》第 5、6 节快照与校算
  - [x] 校算实测：常规 5–6 回合、隐藏 4 回合、Boss 12 回合；Boss 四阶段分别拿到 4 / 2 / 4 / 2 个完整回合
- **为什么动破防比例（原决策未预见）**：破防额外伤害是「目标最大生命 × 比例」且**按段数结算**，一回合最多 4 段。
  取 5% 时单回合峰值达 Boss 最大生命的 **28%**，而四阶段阈值最窄间距只有 25 个百分点——阶段会被整段跳过；
  同时把 Boss 血量从 1400 抬到 3800，回合数几乎不变（10 → 11），血量不再是节奏的主导变量。改为 **2%** 后单回合峰值降到 **17%**，
  四个阶段各拿到 2–4 个完整回合。两处断言都验证过「按旧口径会失败」。
- **被取代的动作**：原落地动作「Boss 阶段二阈值改 0.75」**不再执行**——那条是基于旧版两阶段（50% 触发）方案；
  现方案已是四阶段（1 / 0.7 / 0.4 / 0.15），并由「单回合峰值 ≤ 25%」这条断言统一兜住所有阶段边界，比逐个调阈值更直接。
- **顺序约束**：**已排在 P5 之后** —— 校算基准是首章真实猴妖编成。
- **未随本次决策处理**：《战斗数值 v1》第 7.3 节的四条遗留（破防伤害占比 55–68% 偏高、是否引入独立暴击率、相生是否参与战斗、隐藏遭遇的节奏目标）。**首轮仍为未决，第二轮已关闭其中三条**，见下。

- **补记（2026-09-24，第二轮）**：首轮留下的四条遗留里三条已改定，改完重跑校算仍是达标节奏。

## 验收证据（2026-09-24，第三轮：战斗内核 v1）

本轮把「一场仗能从建队跑到胜负」的内核补齐并写进 `Docs/战斗内核-v1.md`。骨架的四条验收标准仍然适用：

|---|---|---|
| 能编译 | 通过 | 修掉测试程序集里一处 `error CS`（见下），之后 EditMode 与 PlayMode 两套都跑到出结果 |
| 能出包 | **本轮未跑** | 本轮只动运行时与测试，没有碰构建设置；出包结论沿用第二轮的 72 MB / 58.0 秒 |
| 测试全绿 | 通过 | EditMode **331/331**、PlayMode **15/15**；结果见 `Logs/TestResults/{EditMode,PlayMode}.xml`，`All.status.txt` 写 `passed` |
| 重复数据 ID 会报错 | 通过 | 沿用第二轮证据（本轮未动 `DefinitionCatalog`） |

本轮修掉的问题，以及「先红后绿」的记录：

1. **测试程序集编译不过**：`Tests/EditMode/BattleLab.cs` 写成了 `Object.CreateInstance<T>()`。
   `UnityEngine.Object` 上根本没有这个静态方法（应为 `ScriptableObject.CreateInstance<T>()`），
   于是整套 EditMode 一条结果都产不出来。→ 这是「结果文件缺失 = 编译错误」的典型症状。
2. **`TickCooldowns` 边遍历边赋值**：`Dictionary` 的索引器赋给已存在的键也会推进内部版本号，
   冷却跨过一手时当场抛 `Collection was modified`。断言真的照出了它（先红），改为先抄键再改值（后绿）。
3. **三条用例的速度前提算错**：ATB 的行动值是**累加的行动间隔**，而这三条按「一手一人」设了
   速度 5（间隔 2000），于是「我打一下、敌人接一手」「快者动两次后轮到慢者」这些前提都不成立。
   处理方式是**改用例的数据、不动断言**（`BattleBreakAndStatusTests` 与 `BattleRunTests` 的敌人改为同速 30，
   `BattleSessionTests` 的慢者由速度 10 改为 14，使 2×250 < 714 < 3×250 成立）。
4. `BattleLab.Status` 的攻／防／速修正量默认值原本是 1（加算区的中性值是 0），
   会造出「什么都不写就 +100% 攻防」的假状态，已改回 0。
