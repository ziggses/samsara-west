  - [x] 破防额外伤害口径 `5% → 2%`（`BattleConfig._brokenBonusHealthRatio`）——这是本轮最关键的一处改动，理由见下
  - [x] 新增节奏校算器 `Editor/Tools/EncounterPacingEstimator.cs`（菜单 `SamsaraWest/数据/战斗节奏校算`）
  - [x] 新增断言 `Tests/EditMode/EncounterPacingTests.cs`：常规 4–6 回合、Boss 10–15 回合、单回合不得吃掉 Boss 25% 以上最大生命
  - [x] 同步《战斗数值 v1》第 5、6 节快照与校算
  - [x] 校算实测：常规 5–6 回合、隐藏 4 回合、Boss 12 回合；Boss 四阶段分别拿到 4 / 2 / 4 / 2 个完整回合
- **为什么动破防比例（原决策未预见）**：破防额外伤害是「目标最大生命 × 比例」且**按段数结算**，一回合最多 4 段。
  取 5% 时单回合峰值达 Boss 最大生命的 **28%**，而四阶段阈值最窄间距只有 25 个百分点——阶段会被整段跳过；
  同时把 Boss 血量从 1400 抬到 3800，回合数几乎不变（10 → 11），血量不再是节奏的主导变量。改为 **2%** 后单回合峰值降到 **17%**，
  四个阶段各拿到 2–4 个完整回合。两处断言都验证过「按旧口径会失败」。
- **被取代的动作**：原落地动作「Boss 阶段二阈值改 0.75」**不再执行**——那条是基于旧版两阶段（50% 触发）方案；
  现方案已是四阶段（1 / 0.7 / 0.4 / 0.15），并由「单回合峰值 ≤ 25%」这条断言统一兜住所有阶段边界，比逐个调阈值更直接。
- **顺序约束**：**已排在 P5 之后** —— 校算基准是首章真实猴妖编成。
- **未随本次决策处理**：《战斗数值 v1》第 7.3 节的四条遗留（破防伤害占比 55–68% 偏高、是否引入独立暴击率、相生是否参与战斗、隐藏遭遇的节奏目标）。**首轮仍为未决，第二轮已关闭其中三条**，见下。

## 第七轮补记（2026-10-08）：批次 4 · 防御落地

前三项待办的推进顺序是「先做已拍板的，再等设计的」。本轮把**已拍板但没写码**的**批次 4（防御）**做完了。

## 第九轮补记（2026-10-08）：战斗界面 · 诊断层视图

前两轮把界面回路做成了「能点的接口」（`BattleHudModel` + `BattleScreenController`，
两边都在 EditMode 里逐条锁死），但它们**没有任何视图**：`OnGUI` 一行都没有，
全工程 0 个 prefab、除 Bootstrap 外 0 个场景。本轮补上这一层——`BattleScreenView`，
**内核与回路都没改**（`RefreshCommands` 给什么就画什么，点了就转发）。

- **为什么是 IMGUI 诊断层**：与 `SkeletonBootScreen` 同一条理由，也沿用同一条先例——
  ADR-014 的正式界面（uGUI + TMP）需要一套带中文字形的字体资产，工程里还没有；
  若本层强依赖它，就会在「字体还没做」的现在一个字都画不出来，正好失去意义。
- **为什么自挂**：这一层要回答的问题是「界面拿到的这一手，点下去到底会怎样」。
  工程里没有任何流程会在一场仗开始时把它带起来，若要靠场景接线，漏挂时它会静默缺席。
  `[RuntimeInitializeOnLoadMethod]` 自挂之后，**用例不必先搭场景就能验它**。
- **它不含任何战斗规则**：单位行、意图预告、按钮、候选全部照抄 `BattleHudModel`；
  置灰的按钮**不转发**内核（界面已经知道它必然被拒，转过去只会往战斗日志里写「点了没用」）；
  拒绝理由也只是把 `BattleCommandOption.Rejection` / `LastResult.Rejection` 转述成文本键。
- **子选择归界面自己管**：`移动`／`换位`点开的是选落点／选同伴（`PickLabels` + `PickKeys`），
  随时可 `CancelPick()` 撤回；选目标的候选仍然只问驱动器。子选择不会替玩家推进战局。
- **服务重装后重新解析**：视图记下自己解析过的那张注册表，换了一张（组合根每次安装都新建一张）
  就把缓存整个丢掉重来。否则退出／重跑流程之后，它会攥着上一轮的对象继续画——这一条也是
  让 PlayMode 用例能连续跑同一个实例的前提。
- **诊断入口**：`StartDiagnosticBattle()`（默认 `ENC_CH01_001`）用**真实遭遇与真实队伍**开一场，
  已有战斗进行中时拒绝、不抢。键位上 `F2` 开一场、`F3` 收起面板；`F2` 只在编辑器与开发版给
  （与 `ErrorOverlay` 同一条口径：正式包里不该有一个按键能凭空开战），`IsDiagnosticStartSupported`
  公开出来就是为了让用例不必猜这条规则。面板画在**左下角**，与左上角的骨架自检画面互不遮挡。
- **动了哪些文件**：新增 `UI/Runtime/Battle/BattleScreenView.cs`、`Tests/PlayMode/BattleScreenViewTests.cs`；

  5 条：不接线也能出现、用真遭遇开一场、拒绝顶掉进行中的战斗、**只靠点按钮把一整场仗打完**、

## 第十一轮补记（2026-10-08）：装备与经文加成接入战斗（属性聚合层）

这一轮修的是**静默失效**：装备与经文的数值此前只是「表里有、能查到」，没有任何运行期消费点，

- **聚合唯一真源**：`Data/Runtime/CharacterStats.cs` 的 `CharacterStatsResolver`——「角色基础值 + 在身装备 + 经文」，

  由 `BattleFactory` 在建场时写进战斗日志。**一件坏装备不会让人开不了战，也不会被悄悄吞掉。**

## 第十三轮补记（2026-10-08）：技能挂载——装备与经文带来的技能接进战斗

## 第十四轮补记（2026-10-08）：被动——身份登记一张新表，效果落在常驻状态上

装备与经文的 tooltip 从第一版起就写着「被动生效」，而工程里既没有「被动」这种定义，
也没有任何表达「不占行动、常驻生效」的载体（第十三轮只落了技能挂载，见 ADR-019 与上方第 8 条）。

- **被动只登记身份**：新增 `passives.csv`，与其它定义表同构，唯一与玩法有关的列是 `statusId`——效果写在那条状态上。
  分工只有一句话：**状态回答「会发生什么」，被动回答「这是谁给的」**。ID 前缀 `PSV_`（`IdRules` 第 18 条正则），
  映射写进 `DefinitionImportMap`，于是导入、校验、目录装配、本地化键扫描**全部自动认识它**，没有第二处表清单。

- **常驻是状态自己的一列**：`statuses.csv` 加 `permanent`（真源在 `StatusDefinition.IsPermanent`）。

## 第十五轮补记（2026-10-08）：探索运行时落地——走格／交互／掷遭遇，接线留在组合根

多轮「仍未做」里挂着的那条**探索运行时**（`Exploration/` 只有空 asmdef + 接口契约）本轮填上了。
口径见 **ADR-021**；**数据表一行没改**，只消费既有的 `maps.csv` 与 `interactables.csv`。

- **依赖方向是本轮的主语**：`Exploration` 只依赖 Core + Data——它读地图与交互物、发事件，但**不认识**
  `IBattleService`、场景与界面。于是 `Flow` 的引用清单加上 `SamsaraWest.Exploration`（`ProjectSkeletonTests`
  锁住），因为**组合根要替「遇敌 → 开战」接线**；否则探索就得引用战斗，模块边界会从编译期约束退化成一句口号。
- **服务与会话分工同 `Battle`**：`IExplorationService` 长期存活，只管「开一次 / 记住当前这次」，换图丢会话；
  `ExplorationSession` 有始有终，只做三件事——走一格、交互一次、掷一次遭遇。
- **走格顺序固定**：`TryMove` 先判**遭遇挂起**、再判越界、再判占格；走成才更新朝向与步数、发 `PlayerMovedEvent`，
  **最后**才掷遭遇（「这一步先发生，再决定要不要遇敌」）。**撞墙不改朝向**，于是「面朝哪」永远等于「上一次走成的方向」。
- **交互看的是面朝那一格**：交互物占格且不可进入，玩家永远站在它**旁边**，所以「面向」是必要条件。
  拒绝分五种理由（`NoTarget` / `Hidden` / `RequirementNotMet` / `AlreadyUsed` / `EncounterPending`），
  且**拒绝不发事件**——事件只报告真的发生了的事。一次性交互物**先记账再发事件**，订阅方不必自己防重入。
- **换图是数据判据不是类型键**：交互物的 `targetId` 只要是合法地图 ID，这次交互就额外发一条 `MapChangeRequestedEvent`，
  由流程侧决定何时真的换。
- **条件是注入的状态源**：`IExplorationStateSource` 是「剧情状态 → 数值」的单向读取口，缺省实现**全读 0**——
  这是**诚实的退化**：状态那本账还没人写，带条件的交互物因此按「条件未满足」隐藏，而不是被当成已满足放出来。
  `RefreshVisibility()` 按新状态重建格，触发点是「条件键变了」那条事件（剧情侧发），所以它自己**不再发事件**。
- **遭遇只掷骰与报告，不开战**：走 `RandomStreams.Exploration` 命名流（调战斗数值不连带改路边遇敌序列）；
  `IsSafeZone` 的地图**即便表里填了概率也不掷**——这条比数据校验硬：校验只警告，运行期必须真的不发生。
  掷中只挂起 `PendingEncounterId` 并发 `EncounterTriggeredEvent`；挂起期间移动与交互都被拒，否则连点两下会连开两场战斗。
- **接线落在 `Flow/ExplorationBattleLink`**：遇敌 → 查遭遇定义 → 取默认队伍（`BattleFactory.DefaultParty`，骨架期口径）
  → `FromEncounter` + `Validate` → `IBattleService.StartBattle`；战斗结束（`BattleEndedEvent`）→
  `ExplorationSession.ResolveEncounter()`，**漏了这一步玩家在原地一步都走不动**。
  **遭遇当场失效就不开战、也不了结**（查不到定义／队伍为空／入场清单不合法）：记错误日志并**留着那次遭遇**
  （`IgnoredEncounters` 计数），玩家能看见「这里卡住了」，而不是带着一个静默消失的遇敌继续走。
- **引导期顺序**：`GameBootstrap` 在 `Battle` 之后装 `Exploration`（两者都要读 Data），**最后**建接线（它要两个服务）；
  `OnDestroy` 里先 `Dispose()` 掉接线再清服务，`Dispose` 幂等。剧情状态源**暂时不注入**——那本账还没有人写。
- **动了哪些文件**：新增 `Exploration/Runtime/`（`ExplorationTypes.cs`／`ExplorationEvents.cs`／`ExplorationStateSource.cs`
  ／`ExplorationGrid.cs`／`ExplorationSession.cs`／`ExplorationModule.cs`，**6 个文件**与 `Runtime.meta`）、

## 第十六轮补记（2026-10-08）：探索可玩入口落地——自挂面板、字符格子图、UI 允许读玩法模块

第十五轮的成本栏里钉着一句「**探索没有可玩入口**——没有场景、没有渲染、没有输入绑定，测试是唯一的使用者，
**『探索可玩』不成立**」。本轮把那句话里**先能做的那部分**做掉：走格真的能在游戏里走。口径见 **ADR-022**；
新增 **1 个可玩入口（诊断层）**，`UI` 的引用清单加一条；**数据表一行没改**——连 `maps.csv` 与
`interactables.csv` 都没碰。仍然 **0 个 prefab、0 张切片、0 个新场景**。

- **不做场景接线，仍然自挂**：工程里没有任何流程会在「一张图被打开时」把界面带起来，靠场景接线的话
  漏挂就是静默缺席，人也就永远核对不到这一层。于是与 `SkeletonBootScreen`、`BattleScreenView` 同一条路：
  `RuntimeInitializeOnLoadMethod(AfterSceneLoad)` 自己挂上来。**自挂不是偷懒，是把「谁来带起它」这个还
  没有答案的问题先绕过去**——正式场景做出来的那天，`Enabled=false` 一个开关就能让它退场。
- **用 IMGUI 画字符格子图，不引资产**：ADR-014 的正式界面（uGUI + TMP）要一套带中文字形的字体资产，
  正式场景还要瓦片图与角色图，工程里都还没有。格子图就用 `@`（自己）／`*`（面朝）／`#`（交互物）／`.`（空地）
  画出来，**代价是丑，收益是今天就能真的走**。行序必须反过来画：内核 Y 向上、屏幕 Y 向下，照内存顺序画
  会让人觉得自己在倒着走北。
- **输入只用 IMGUI 事件**：与另两层同一取舍，用 `UnityEngine.Input` 在「仅 Input System」的后端下会直接抛异常。
  方向键与 `WASD` 等价（`DirectionOf` 纯函数，用例单独钉住映射），`E`／`Space`／`Enter` 交互；
  `F3` 收起面板（与战斗面板共用）、`F4` 进图／离图（只在编辑器与开发版给，**正式包里不该有一个按键能凭空传送**）。
- **面板不含探索规则**：能走到哪、能不能交互、遭遇掷没掷中，全是 `ExplorationSession` 说了算；本层只把
  结算结果如实地画出来。它**不认识战斗**——遭遇怎么变成一场仗是 Flow 侧 `ExplorationBattleLink` 的事，
  面板只把 `PendingEncounterId` 画在状态行上。
- **拒绝文案的口径与战斗刻意不同**：战斗的置灰理由只转述「玩家改操作能绕开的」，其余由界面拦下；
  探索没有按钮可置灰——玩家按的是方向键，拒绝只表现为「人没动」，所以**移动的三种拒绝全部给文案**
  （越界／占格／遭遇挂起），**按了没反应必须有一行字解释**，否则玩家会先怀疑按键丢了而不是先怀疑墙。
  唯一不给文案的是交互的**「藏起来了」**（`Hidden`）：那句话等于替数据宣布「这里有个机关，只是现在看不见」，

## 第十七轮补记（2026-10-08）：剧情状态账落地——账有人写了，条件交互物会当场显隐

前两轮的成本栏都钉着同一句：「**剧情状态源还没人写**，因此所有带条件的交互物现在都隐藏（诚实地退化成
『看不见』），且状态变更要人手调 `RefreshVisibility()`」。本轮把那句话里的**机制**做掉。口径见 **ADR-023**；
新增 **1 个模块实现（Narrative，此前是空壳）**、**2 条 Flow 接线**；**数据表一行没改**。

- **账本落在 `Narrative`**，不是 Core：它是「剧情状态」，与战斗、探索同级的玩法模块。一本「状态键 → 整数」的账，
  外加心念三轴。只依赖 Core 与 Data（骨架测试锁住），事件总线是软依赖——没有总线也能读写，只是不通知。
- **契约早就写好了，本轮只是把它实现出来**：任务的目标键（`objectiveStateKeys`）、对话的进入条件与写入
  （`requiredStateKey` / `setsStateKeys`）、结局的判据（`requiredStateKeys` + 三条 `min*`）、探索的条件交互物——
  四张表用的是**同一套语言**（状态键 + 运算符 + 数值），所以共读一本账；`SaveData` 的 `FlagKeys` / `FlagValues`
  与三轴字段也早就留着。**没有设计新东西**，只是把数据层已经宣布的契约兑现出来。
- **心念只能累加，不能赋值**：数据里它从不出现在 `setsStateKeys` 里，只以 `karmaChannel` + `karmaDelta` 的形式累加。
  所以往 `karma.*` 键上 `SetValue` 会被记日志并忽略——否则一次「赋值」会把攒了几章的累加值悄悄换掉。
  但**读**口认得 `karma.*`：键的格式规则允许它，理论上有人会拿它当交互物条件（「慈悲 ≥ 30 才开的门」），
  读口若一律返回 0，那扇门会永远打不开且看不出为什么。
- **值真的变了才发事件**：同一个键写成同一个数不发。探索侧靠这条事件重建可行格，重复发会让一次开门引出两条刷新；
  写回 0 等于抹掉那条记录，快照里不留没用的 0。
- **坏键进不来**：不符合 `flag./relation./karma./ending.` 规则的键记错误并忽略，日志里带上那个键。账本是全局的，
  一个拼错的键若静默生效，排查成本极高。
- **探索怎么读到它——中间隔一层适配器，不是把接口搬进 Core**：`Narrative` 不许认识 `Exploration`，
  `Exploration` 也不认识 `Narrative`（两边都由骨架测试锁住）。都认识两者的地方是组合根，所以
  `Flow/NarrativeStateSourceAdapter` 只转一个 `GetValue`。这里**刻意没有**把只读口提升到 Core：
  今天读这本账的只有探索一家，而 ADR-021 的口径本来就是「不预建只有探索在用的全局状态服务」；
  将来任务与结局也要读同一本账时再提升（登记在 ADR-023）。
- **「状态变了 → 重建可行格」落在 `Flow/NarrativeStateLink`**：与 `ExplorationBattleLink` 同一条理由——
  它是唯一同时看得见账本与探索的那条线。**两条事件都听**（`flag.*` 与 `karma.*` 都可能出现在条件键里）。
  不在图上时什么都不做：账本可以在进图前就被改，而进图那一刻本来就按当前账本建格。
- **为什么不做「事件升到 Core」**：事件要能被「重建格」与「重画界面」两方听到，直觉上该进 Core。
  但诊断界面本来就靠 0.5s 兜底间隔重画，**不需要订阅**；于是跨模块订阅方实际只有一条线，
  放在组合根比在 Core 开「领域事件」的先例更省。等真有第二个订阅方（任务面板、结局判定）时再议。
- **动了哪些文件**：新增 `Narrative/Runtime/{KarmaAxis,StoryState,NarrativeEvents,NarrativeModule}.cs`、
  `Flow/Runtime/{NarrativeStateSourceAdapter,NarrativeStateLink}.cs`、`Tests/EditMode/StoryStateTests.cs`（新 12 条）、
  `Tests/PlayMode/NarrativeStateLinkTests.cs`（新 3 条）；改 `Flow/SamsaraWest.Flow.asmdef`（加 `SamsaraWest.Narrative`）、
  `Flow/GameBootstrap.cs`（装 Narrative、注入适配器、建接线、暴露 `NarrativeLink`）、
  `Tests/PlayMode/GameBootstrapLifecycleTests.cs`（模块清单加 Narrative，并补一条端到端断言：探索的条件源真的接在账本上，
  而不是「全读 0」的替身）。文档：`Docs/架构决策.md`（ADR-023、模块表、ADR-013 补记、未决第 5 条三记）、
  本文件、`README.md`。**战斗、探索内核、数据与存档一行没改**；`Narrative` 的 asmdef 引用也没变
  （它本来就只依赖 Core + Data）。
- **测试**：EditMode **529 → 541**（新 12 条：未写键读 0、写读往返、写回 0 抹记录、坏键被拒、同值不重复发事件、

## 第十八轮补记（2026-10-08）：换图接线落地——首章第一次能连着走

ADR-022 的成本栏钉着一句「`MapChangeRequestedEvent` 目前**只被画出来、没有订阅方**（换图接线在 Flow 侧仍未做）」。
本轮把那根断线接上。口径见 **ADR-024**；新增 **1 条 Flow 接线**（`MapChangeLink`）、**1 个事件字段**、
**1 条进图路径**（`EnterMapNear`）、**1 条网格纯函数**（`NearestWalkable`）、**2 扇门**——
数据表**第一次动行**（前几轮都写着「一行数据都没改」），但**列一个没加**。

- **换图落在组合根，不在探索里**：探索只发请求、不换图。「谁来加载、落在哪」既关场景又关流程，
  而探索不认识这两样（ADR-021 的边界）。所以新增的 `Flow/MapChangeLink` 是唯一同时看得见
  「探索的请求」与「目标图存不存在」的那条线，写法与 `ExplorationBattleLink`、`NarrativeStateLink` 同一种。
- **事件为此扩了一个字段**：`MapChangeRequestedEvent` 带上 `Position`（门在**来源图**上的格子）。
  落点口径是「目标图里离这扇门最近的可行走格」，而**发事件的一方知道门在哪、订阅方不知道**——
  少带这一个字段，订阅方就只剩「随便落在哪」一种选择。这是本轮唯一一处接口改动。
- **落点靠一条几何规则，不靠新数据**：把门的坐标拿到目标图上，先夹进边界；夹过的格若可走就用它，
  否则按切比雪夫环由内向外找第一格可走的。环内顺序固定：先四个正方向（上 → 右 → 下 → 左），再扫其余格。
  先正方向是因为「站在门正上方」比「站在门口斜角」更像玩家预期；顺序固定是因为落点要可复现、将来要能写进存档。
- **进图分成两条路，分歧正是重点**：`EnterMapNear`（换图用，锚点站不住就就近挪一把）与 `EnterMap`（读档用，
  坐标是玩家自己走出来的，越界或被占说明数据坏了，那时该留下痕迹而不是悄悄替玩家挪个地方）。
  两者共用同一个壳，差别只有「落点算不算」。
- **先验证再离图**：目标图不在定义目录里时**不动当前会话**，只记一次忽略。先离图再发现目标查不到，
  玩家就会掉进「哪张图都不在」的状态。门指向自己所在的图同样忽略（等于让玩家原地卡一次读图）。
- **首章此前一扇门都没有**：`interactables.csv` 那三条交互物分别指向对话、查看、开箱，**没有任何 `targetId`
  指向地图**——也就是说这条链在真实数据下永远不会触发，此前只有 EditMode 用例在手工造门。
  本轮补上 `INT_CH01_004_ROAD_GATE`（山道图 (18,6) → 小镇图）与 `INT_CH01_005_TOWN_GATE`
  （小镇图 (15,5) → 山道图），外加 `ui.prompt.enter` 与四条文案。
- **两扇门的位置是对着选的**：小镇图比山道图小（16×10 对 20×12），(18,6) 越界，夹回来是 (15,6)——
  正好落在回程门 (15,5) 的正南面，进门一步就看见回去的路。**先挑落点、再倒推门位**：落下就被丢到
  地图另一头，是最容易让人以为「走错了」的那种体验。
- **动了哪些文件**：新增 `Flow/Runtime/MapChangeLink.cs`；测试新增 14 条用例（EditMode
  `ExplorationGridTests` 落点 6 条 + `ExplorationWiringTests` 换图接线 5 条；PlayMode
  `ExplorationScreenViewTests` 端到端 3 条，全部追加在既有文件里，没有新开测试文件）。
  改 `Exploration/{ExplorationEvents,ExplorationGrid,ExplorationModule,ExplorationSession}.cs`、

## 第十九轮补记（2026-10-08）：存档接线落地——账本、位置与随机种子第一次能跨重启

ADR-023 与 ADR-024 的成本栏都钉着同一句「账本**不进存档**——`SaveData` 字段留着但没人搬，重启即清零」。
本轮把那句话兑掉。口径见 **ADR-025**；新增 **1 条接口**（`ISaveCoordinator`，落在 `Save`）、
**1 个实现**（`Flow/SaveCoordinator`）、**1 条接线**（`InteractionFlagLink`）、**1 条事件**（`StoryStateRestoredEvent`）、
**1 个键约定**（`InteractableFlags`）、**1 层诊断入口**（`SaveScreenView`，`F5` 存 / `F9` 读）、
**1 处模块依赖**（`UI` → `Save`）。数据表**一行没改**，`SaveData` 的字段**一个没加**。

- **搬运落在组合根，接口留在 `Save`**：契约在 `Save/Runtime/ISaveCoordinator`，实现在 `Flow/Runtime/SaveCoordinator`。
  搬运要同时认识探索（位置）、剧情（账本）与随机（母种子），而 `Save` 只依赖 `Core`——
  把它写进 `Save` 就得让存档模块反向去认识玩法，正是 ADR-001 那张表想拦下的方向。
- **界面因此多了一条依赖**：`UI` 不许认 `Flow`（骨架测试锁住），而「按一下存、按一下读」总得有人接。
  于是 `UI` 的 asmdef 加了 `SamsaraWest.Save`，面板只认 `ISaveCoordinator`——它知道「世界上有存档这件事」，
  不知道是谁、按什么顺序装起来的。骨架测试里那条「UI 不得依赖 Flow」旁边，现在多了一条「但必须能读存档搬运接口」。
- **账本整本进出，不逐键搬**：`IStoryState` 新增 `Values` 快照与 `Restore(值表, 心念三轴)`。
  读档是「换成另一份状态」而不是「在当前状态上叠加」——上一局留下的键若跟着过来，玩家要读档之后才会发现。
  **逐键搬也不现实**：一次几百条 `StoryStateChangedEvent` 会让 `NarrativeStateLink` 把可行格重建几百遍。
  于是账本另发一条「整本换掉了」，`NarrativeStateLink` 从听两条变成**听三条**。
- **两处顺序是有意的**：**先校验、再动状态**（存档指向的图查不到就整份退回，免得留下「账本换了、人还站在旧图上」）；
  **先复位母种子、再进图**（探索流是进图那一刻取的，晚一步复位，这一次进图就落在旧种子的序列上了）。
  读档恢复位置走 `EnterMap` 而不是 `EnterMapNear`——存档里的坐标是玩家自己走出来的，越界或被占说明数据坏了，
  那时该留下痕迹而不是悄悄替玩家挪个地方（ADR-024 埋的两条进图路径正好在这里分岔）。
- **一次性交互物「用过了」一并进账**：ADR-024 成本栏里那句「换图即丢、开过的箱子会复活」，
  本轮就是它说的「等账本进存档时一并处理」。键的约定是 `flag.interact.<小写交互物 ID>`；
  **写**的一侧只听 `OneShot`（查看、对话这类可重复的不记——记下来，第二次交互会被当成「已用过」而拒掉），
  **读**的一侧是 `ExplorationSession.HasUsed` 自己往条件源问一句。所以这是一条**只写不读的单向线**：
  读档时账本整本灌回来，下次进图的判定自然就对。
- **诊断入口画在左下角**：左上角已经被探索面板占着，两个诊断层叠在一起会互相遮住，
  而它们要同时看得见才核对得动（存之前先看一眼人在哪、账记了几条）。文案全走文本表，新增 8 条 `ui.save.*`。
- **动了哪些文件**：新增 `Save/Runtime/ISaveCoordinator.cs`、`Flow/Runtime/SaveCoordinator.cs`、
  `Flow/Runtime/InteractionFlagLink.cs`、`Exploration/Runtime/InteractableFlags.cs`、
  `UI/Runtime/Save/{SaveTextKeys,SaveScreenView}.cs`；改 `Narrative/Runtime/{StoryState,NarrativeEvents}.cs`、
  `Exploration/Runtime/ExplorationSession.cs`（`HasUsed` 并账本）、`Flow/Runtime/{GameBootstrap,NarrativeStateLink}.cs`、
  `UI/SamsaraWest.UI.asmdef`。测试新增 3 个文件（`Tests/EditMode/{InteractionFlagLinkTests,SaveCoordinatorTests}.cs`、
  `Tests/PlayMode/SaveScreenViewTests.cs`）、改动 3 个（`Tests/EditMode/{StoryStateTests,ProjectSkeletonTests}.cs`、
  `Tests/PlayMode/GameBootstrapLifecycleTests.cs`），并修了 1 条会时红时绿的旧用例（见下）。

  文档：`Docs/架构决策.md`（ADR-025、模块表、未决第 5 条五记）、本文件、`README.md`。
  **战斗内核、数据表与探索内核的行为一行没改**。
- **卡了一次「先有鸡还是先有蛋」**：`SaveTextKeys` 引用的是**导入才会生成**的常量，而导入又要求先编得过——

## 第二十轮补记（2026-10-08）：战果回写落地——打完一场，结局第一次留在账本里

《战斗内核 v1》第 11.1 节第 7 条钉着「**仍缺**……以及**战后结算与剧情回写**（胜负奖励、剧情分支）」，
而 `BattleModule.EndBattle()` 的注释里早就留了缝——「战后结算完成、**进入下一段剧情时**」才该丢掉会话。
本轮把「剧情回写」这半句里的**机制**做掉。口径见 **ADR-026**；新增 **1 个键约定**（`Flow/BattleFlags`）、
**1 条接线**（`Flow/BattleStoryLink`）、**1 个事件字段**（`BattleEndedEvent.EncounterId`）。
数据表**一行没改**，生成物**一个没动**（本轮不碰本地化），`BattleModule` 的行为也**一行没改**
（只动了它广播的事件带什么）。

- **先补齐事件的不对称**：`BattleEndedEvent` 原来只有 `Outcome / Rounds / ActionCount`，而开打事件
  `BattleStartedEvent` 带 `EncounterId`——开打知道是哪一场、打完不知道。归因信息缺了这一块，
  就只能让组合根自己记住「最近一次开打是谁」，那是把状态塞回不该有状态的地方。
  于是给它补上 `EncounterId`（与开打事件对称），**没有遭遇 ID 时为空串**，明确表示「无法归因」，
  而不是臆造一个。
- **写的一侧是 `Flow/BattleStoryLink`**：订阅 `BattleEndedEvent`，按结局往账本写
  `flag.battle.<小写遭遇 ID>.won|lost|fled|retreated`（一个结局一个键、值为 1，与上一轮的
  `flag.interact.<交互物>` 同一种口径）。战斗内核**不认识账本**（连 `Narrative` 都不引用）、
  账本也**不认识战斗**，两边都认识的地方只有组合根——所以这条订阅落在 `Flow/`，与四条既有 Link
  同一种写法。它**只写不读**：读它的是内容表里的条件（数据，不是代码），以及将来的对话／任务。
- **撤退绝不写 `lost`**：已拍板口径是「剧情撤退不算失败、回到剧情前的节点」，所以它写 `retreated`。
  这条话说到底只在 `BattleOutcome.ForcedRetreat` 的备注里躺着，本轮第一次落到流程侧，
  并且用**两个方向**钉住：记了 `retreated`（是事实），且 `lost` 必须为 0（不是战败）。
  把撤退记成战败，会让剧本里「输过一次」「打赢过」这类条件判错，而且错得很安静。
- **不记的三种情形**：没有遭遇 ID（手工构造的战斗，没法归因）记 `UnattributedOutcomes` 并警告；
  结局不是收场（`Ongoing` 或未知值）记 `UnrecognisedOutcomes` 并报错；键在账本里已经有值则**跳过**
  （同一场在别的会话里打过，或存档刚灌回来）——三个计数供诊断与测试。
- **刻意不丢战斗会话**：`BattleStoryLink` **不**调 `IBattleService.EndBattle()`。内核注释写明那是
  「进入下一段剧情时」的事，而现在还没有「下一段剧情」；`BattleScreenView` 还在每帧读 `Current`
  显示结局，提前丢掉会让玩家看不到自己是怎么赢的。**这条缝继续留着**。
- **动了哪些文件**：新增 `Flow/Runtime/BattleFlags.cs`、`Flow/Runtime/BattleStoryLink.cs`、
  `Tests/EditMode/BattleStoryLinkTests.cs`、`Tests/PlayMode/BattleStoryWiringTests.cs`；
  改 `Battle/Runtime/BattleEvents.cs`（补 `EncounterId`）、`Battle/Runtime/BattleSession.cs`（发布时带上它）、
  `Flow/Runtime/GameBootstrap.cs`（末尾装接线、`OnDestroy` 释放、暴露 `BattleStory`）。
  文档：`Docs/架构决策.md`（ADR-026、Flow 模块职责行）、`Docs/战斗内核-v1.md`（事件表、第 9 节接线清单、
  第 11.1 节第 7 条）、本文件、`README.md`。**Narrative / Exploration / Save / UI 的代码一行没改**。
- **测试**：EditMode **578 → 591**（新 13 条：四种收场各记各的键、一场只留一个键、两场各留各的、
  同一场记两次只记一次、没有遭遇 ID 不记且计数、没打完不记且计数、退订后不再听、不覆盖既有键、
  三种收场键都过 `IdRules.IsValidStateKey` 且遭遇 ID 转小写、**打赢之后按战果设条件的交互物当场出现**），全绿。
  PlayMode **42 → 45**（新 3 条，真装配 + 真数据 + 真战斗）：**真打一场的结局留在账本里**、
  `ForceRetreat` 只留 `retreated` 不留 `lost`、**战果随 `ISaveCoordinator.Capture().FlagKeys` 走出去**。
  最后一条正是「**战斗 → 剧情状态 → 条件交互物显隐 → 存档携带**」这条链第一次闭环的证据。
- **仍未做**：**只记结局，不记奖励**——掉什么、给多少钱属于战利品与经济，那两块还没有运行期真源，
  这一层**不发明数值**，需要奖励时由内容侧去读这个键；**剧情分支没做**（没有 Ink，键先备着）；
  **战斗场景与界面仍未做**（全项目 0 个 prefab），本轮的成果要在测试与日志里看；
  键一旦落进存档就是**存量数据的契约**，将来改词或改大小写口径就是一次存档迁移的事（ADR-007）；
  联合技（批次 5，等设计）、装备的运行期来源也照旧没动。出包与冷启动构建本轮没跑。

## 第二十一轮补记（2026-10-08）：经济落地——打赢一场，钱与物第一次真的落到玩家身上

上一轮的「仍未做」第一条写着「**只记结局，不记奖励**——掉什么、给多少钱属于战利品与经济，
那两块还没有运行期真源」，更早的 ADR-025 也钉着「背包、货币……统统没进档」。本轮把那几句一起兑掉：
新增 **1 个模块**（`Economy`）、**2 条 `Flow` 接线**（`LootBattleLink`、`VaultBattleInventory`）、
**1 个结算纯函数**（`LootResolver`）。口径见 **ADR-027**。数据表**一行没改**，
生成物**一个没动**（本轮不碰本地化），**战斗内核与探索内核的行为一行没改**。

- **经济是独立模块，谁都不认识它、它也不认识玩法**：`Economy` 只依赖 `Core` 与 `Data`。战斗内核
  连 `Economy` 都不引用，经济也连 `Battle` 都不引用——两边都认识的只有组合根。战斗侧要的
  `IBattleInventory` 由一个**翻译**（`Flow/VaultBattleInventory`）顶上去：它此前在正式流程里
  一直是 `null`，道具指令问谁都要不到东西；接上之后掉落的丹药第一次能在战斗里用掉一个。
  手法与 `NarrativeStateSourceAdapter` 完全一样。
- **结算是一个纯函数**：`LootResolver.Resolve(encounter, definitions, stream, report) → BattleSpoils`，
  不碰注册表、不写日志、不改状态——「掷出来什么」与「记到账上」是两件事，后者交给接线。
  掷骰顺序**有意定死**（按 `enemyIds` 出现顺序逐只敌人，先必掉再抽 `dropRolls` 次）：
  顺序一变，同一种子掷出的东西就变了，而「同一种子必然同一结果」正是随机服务存在的理由（ADR-005）。
- **只有 `PlayerVictory` 结算**：战败、逃跑与剧情撤退都不发东西——《战斗内核 v1》第 11.2 节
  早就把「撤退不结算奖励」写成了口径，这条线是它第一次真的落地。撤退也发奖励的话，玩家会发现
  「打不过就退」比打赢更划算。**不设「一个遭遇只结算一次」**：探索遭遇本来就可重复触发，

## 第三十一轮补记（渲染层底座，ADR-032）

> 落地的是探索画面的**第一层真画面**：底图、交互物、角色用 `SpriteRenderer` 按网格摆位，相机跟随整格吸附。
> 素材来自外部目录 `E:\tx2\素材`（`Assets/_External` 是目录联接、不入库），导入参数由 `AssetPostprocessor` 按代码统一钉住，
> 不靠提交 `.meta`。全项目**仍然 0 个 prefab**——精灵层是运行时代码自挂的，不是从场景里拖出来的。
> 改动 41 个文件、+2692/−13（不含本节）；EditMode 724/724、PlayMode 84/84 全绿。

- **选 SpriteRenderer 而不是 Tilemap**（ADR-032）：Tilemap 的价值几乎全在编辑器里刷格子，而今天的地图排版
  （`maps.csv` 只有尺寸、底图键、原点偏移）**根本不在 Unity 里**——没有 Tile 资产、没有按格摆放的地形数据，
  上 Tilemap 等于先造一套用不上的编辑器工作流。运行时用同一份数据摆 `SpriteRenderer`，将来真要换 Tilemap，
  只需换掉 `ExplorationSpriteView` 一层实现。
- **「32 像素」这条链第一次有代码兜底**：PPU 32 ↔ `tilePixelSize` ↔ 相机正交 ↔ 480×270 基线是同一件事的四个说法，
  任何一处靠人手设都会漂。因为 `Assets/_External` 的 `.meta` 不入库，
  导入参数（Sprite/Single/PPU 32/Point/无 mipmap/不压缩/Clamp）必须是**可复现的代码**：
  `ExternalSpritePostprocessor` 在导入时统一钉上，并按路径排除 `_work / _preview / _src / _base_1x`。
- **绑定数据一半是自动的**：图集 JSON 的帧自带 `spriteKey`（`sprite.int.*`），构建器扫出来直接绑，美术改图集这里跟着变；
  只有「整张图就是一个精灵」的（底图、立绘）列在 `sprite-sources.csv` 里，留空即「还在等美术」。产物 `SpriteCatalog.asset` 进版本库。
- **坐标换算只留一份**：`GridGeometry`（格 ↔ 世界，原点左下、Y 向上）为底图、交互物、角色、相机共用；
  角色站的是格子的**底边中点**而不是格中心——立在地上的人站的是地面线，差半格就是陷进地里。
  单独抽一层是因为「底图对得上、物件差半格」最容易发生，也最难从画面上倒推回数值。
- **缺素材是常态，而且是「报出来」的常态**：缺底图铺一块按网格尺寸的暗色（空白会让人以为渲染层没生效，
  有边界的暗底能直接说「图是这么大」），缺交互物素材记进 `MissingKeys` 而**不画洋红占位**。
  构建器把底图缺口、交互物缺口、待交付分开报——缺口数是**随美术交付下降的指标**，不是错误。

## 第三十四轮补记（2026-10-09）：战斗面板第一次画素材——战斗姿态有了消费方

上一轮刚绑上的 `portrait.chr.*.battle` 当天就被画了出来：战斗面板（`F2`）里**己方每个单位占一格**，
按角色定义的 `battlePortraitKey` 从精灵目录取图等比缩画（128×192 的立绘缩成 64×96，宽度按图自己的比例算）。

  它对应的本来就是战斗画面；对话面板该画的是立绘（`portraitKey`），两件事分开记。
- **目录不是服务**：姿态条要的是 `SpriteCatalog`，由界面层自己 `SpriteCatalog.Load()` 取，**不进服务注册表**。
  目录随工程走（`Rendering/Resources`），与「谁先装、装到哪一步」无关；探索层（`ExplorationSpriteView`）
  本来就是这条口径，界面层跟着走即可——`UI.asmdef` 早已引用 `Rendering`，本轮**没有新增依赖**。
- **三种格子、三种说法**：
  - **有键有图** → 等比缩画。宽度按图自己的比例算（2:3 的 128×192 得 64×96，立绘因此不会压扁），
    并上下夹住——哪张素材换成怪比例，坏的也只是这一格，面板撑不破。
  - **有键无图** → 画那枚**洋红叉**（探索层同一枚记号 `PlaceholderSprites.Missing`），但**按方形居中**：
    记号本身是方的，拉成 2:3 会把它扭歪。「键有、图没了」正是构建器缺口报告要盯的那件事。
  - **连键都没有** → **空槽，什么都不画**。
- **为什么第三条要单独分出来**：敌人定义（`EnemyDefinition`）压根没有素材键——它的列里只有 `aiProfileKey`，
  没有任何 `spriteKey`／`portraitKey`。把「没承诺过素材」与「承诺了没给」合成一个「没画出来」，
  界面就再也说不清缺口在哪一侧了（同 ADR-032「缺素材要报出来、但不画占位」的口径）。
- **画法**：`OnGUI` 用 `GUI.DrawTextureWithTexCoords` 把图集里切出来的一块画进屏幕矩形——
  纹理坐标与 `Sprite.textureRect` 同为左下原点，不必翻 y。叠加顺序是「高亮框 → 空槽底色 → 图」，
  高亮框先画且外扩两像素，于是它成为一圈不会被图盖掉的边。倒下只压暗不隐藏（姿态还在，只是不再行动），
