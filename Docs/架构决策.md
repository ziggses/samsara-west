记录《西游：第八十二难》工程底座的决策：**决定了什么、为什么、靠什么强制、代价与边界**。
决策一经落地并进测试即登记；推翻旧决策时不删条目，在末尾追加「已由 ADR-0xx 取代」。

## ADR-001 模块划分与依赖方向写成 asmdef，变成编译期错误

| 模块 | 职责 | asmdef references |
|---|---|---|
| `Core` | 服务定位、事件、时间、随机、对象池、日志 | `Unity.InputSystem` |
| `Data` | ID 规则、定义基类、CSV 解析、导入映射、校验 | Core |
| `Battle` | 伤害纯函数、战斗数值配置 | Core, Data |
| `Save` | 版本化 JSON 存档与迁移 | Core |
| `Localization` | 文本键服务、表资产、常量生成 | Core |
| `Flow` | 启动装配、场景与章节状态、探索与战斗的接线、剧情状态的接线、换图的接线、存档的搬运、战果的回写、战利品的结算、在身清单的接线 | Core, Data, Localization, Save, Battle, Narrative, Exploration, Economy, Equipment, `Unity.InputSystem` |
| `UI` | 本地化标签、运行期错误面板、战斗界面、探索界面（含对白块）、存档界面 | Core, Data, Localization, Save, Battle, Narrative, Exploration, `Unity.TextMeshPro` |
| `Exploration` | 探索运行时（走格、交互、遭遇掷骰） | Core, Data |
| `Narrative` | 剧情状态账（状态键 → 整数、心念三轴），账本整本进出存档（ADR-025）；对话（剧情节点）运行时见 ADR-029；任务运行时未做 | Core, Data |
| `Economy` | 钱袋与背包（金币、物品堆叠）、战利品结算（见 ADR-027）；不认识战斗与在身清单 | Core, Data |
| `Equipment` | 在身清单：谁穿/带了什么（成员 × 栏位 → 定义 ID，8 槽），整本进出存档（见 ADR-028）；不认识战斗与背包 | Core, Data |
| `Progression` | 骨架占位（目录 + asmdef + 接口） | Core, Data |
| `Audio` | 骨架占位 | Core |
| `Editor` | 导入、校验、出包、工具窗口 | 全部运行时模块（`includePlatforms: ["Editor"]`） |
| `Tests/EditMode` | 单元测试 | TestRunner + Editor + 运行时模块（`UNITY_INCLUDE_TESTS`） |
| `Tests/PlayMode` | 场景级测试 | TestRunner + 运行时模块（**不含 Editor**） |

- **为什么**：文档里的依赖约定是君子协定，asmdef 里的依赖是编译错误。
- **强制**：asmdef `references`；`Tests/EditMode/ProjectSkeletonTests` 另外断言关键依赖，防止有人往 `Core` 里加 `Data` 引用。
- **代价**：跨模块取数据必须走 `Data` 的契约类型；新增模块要同时建目录、asmdef 与骨架测试断言。

## ADR-002 服务定位，而非单例泛滥，也不引 DI 框架

`Core/Runtime/Services.cs`：

- `IService { OnRegistered(IServiceRegistry); OnUnregistered(); }`
- `Register<T>(T)` 同时以**契约类型与具体类型**注册；重复绑定到不同实例抛 `InvalidOperationException`
- `Resolve<T>()` 未注册抛 `ServiceNotRegisteredException`；另有 `TryResolve/IsRegistered/Unregister/Clear/RegisteredTypes`
- `Clear()` **逆序**调 `OnUnregistered()`，依赖方先于被依赖方释放
- 门面 `GameServices.Install/Uninstall/Registry`

**跨场景不丢服务**：服务是纯 C# 对象，不挂场景。挂 `DontDestroyOnLoad` 的是 `Flow/Runtime/GameBootstrap.cs` 的引导对象（重复实例自毁，`OnDestroy` 里 `Registry.Clear()` + `Uninstall()`）。

**不引 DI 框架**：当前十余个服务、四个消费方，容器只会把装配代码挪个位置，却带来容器语义与调试成本。用「解析失败即抛异常」换掉「某处为 null 到处空引用」。

**边界**：每个服务必须有「注册 → 解析 → 卸载」的 EditMode 覆盖；运行时模块**禁止**新增静态单例。

## ADR-003 模块间只走类型化事件总线，带频道与弱引用

`Core/Runtime/Events.cs`：

- `EventChannel` 13 项（Core/Data/Flow/Battle/Exploration/Narrative/Progression/Economy/UI/Save/Localization/Audio/Tools）
- `IEventBus : IService`：`IDisposable Subscribe<T>(Action<T>)`、`Subscribe<T>(EventChannel, Action<T>)`、`Publish<T>(T)`、`Publish<T>(EventChannel, T)`、`ClearChannel(EventChannel)`、`ClearAll()`、`SubscriberCount`
- 退订：`Dispose()` 订阅句柄，批量用 `SubscriptionBag`
- 弱引用：目标是普通类/服务时用 `WeakReference`；**lambda、闭包、静态方法用强引用**（无法可靠判活）——注册闭包即自负退订责任
- 发布时清理死订阅；单个订阅者抛异常不中断发布，异常落 `GameLog.Error`

**代价**：事件是运行期契约，编译期不检查有无订阅者，因此关键事件要求消费方有测试。

## ADR-004 可复现随机：PCG 命名流 + 快照

`Core/Runtime/Random.cs`，自实现 **PCG-XSH-RR 32**，不用 `UnityEngine.Random`。

- `GetStream(name)`、`Reseed(ulong)`、`SnapshotAll()` / `RestoreAll(state[])`
- 命名流常量 `RandomStreams.Battle/Loot/Narrative/Exploration/Economy`
- 初始状态 `splitmix64(seed ^ FNV1a(流名))`，**流名只影响初始状态**：改抽卡逻辑不影响剧情序列
- `RandomStreamState` 带 `Name/State/Increment/DrawCount`，`Restore` 校验流名一致
- 工具：`NextUInt/NextFloat/NextInt/NextDouble/Chance/Pick/Shuffle`

**用途**：战斗重放、存档续玩、测试确定性（同种子同结果）。

## ADR-005 时间抽象：可注入的 manual 模式

`Core/Runtime/Time.cs`：`ITimeService` 暴露 `Elapsed/Delta/RealElapsed/Scale/IsPaused/IsManual` 与 `Pause/Resume/Advance/Tick/Reset`。
manual 模式下除 `Advance(seconds)` 以外的驱动调用抛 `InvalidOperationException`，把「时间」变成测试输入。
驱动者 `GameClockDriver` 用 `[DefaultExecutionOrder(-10000)]` 在 `Update` 里 `Tick(Time.unscaledDeltaTime)`。

## ADR-006 对象池只服务高频短命对象

`Core/Runtime/Pooling.cs`：`ObjectPool<T>`（`Get/Release/Prewarm/Clear` + `CountActive/CountInactive/TotalCreated`）、`PrefabPool`（多实例 `Spawn(pos, rot)`）、`PoolService`（`GetOrCreate<T>/GetOrCreatePrefab/TryGet/ClearAll`）。
适用范围：特效、飘字、敌人实例。**不对低频对象做池**（YAGNI，池本身有状态成本）。
已知坑见 README 第 1 条：`DestroyItem` 刻意不用空条件调用（Mono 下会挂死主线程），**不要改回去**。

## ADR-007 日志分层分频道，环形缓冲 + 文件降级

`Core/Runtime/Logging.cs`：`LogLevel`（Trace…Off）、`LogChannel`（同 13 项）、静态门面 `GameLog`（`Configure/AddSink/RemoveSink/EnsureInstalled/Snapshot/Trace…Fatal`）。

- `RingBufferSink` 容量 2048，供日志控制台与错误面板回溯
- `FileLogSink` 写 `persistentDataPath/Logs`，`SubsystemRegistration` 时 `AutoInstall`；WebGL 自动降级
- `ILogSink` 由 `UI/Runtime/ErrorOverlay.cs` 实现，**仅在 Editor 与 Development Build** 生效，发布版只留文件日志
- 纪律：不打印个人信息与大对象；高频路径不拼字符串（用结构化字段）

## ADR-008 数据以 ScriptableObject 为唯一真源，CSV 只是输入面

`DefinitionBase` 定义统一契约：`Id / DisplayNameKey / DescriptionKey / Tags / Version / Icon` + `abstract DefinitionKind Kind` + `virtual Validate(ValidationReport)`。
所有 ID 规则集中在 `Data/Runtime/Ids.cs` 的 `IdRules`（按 `DefinitionKind` 查编译好的正则），**禁止在业务代码里散落 ID 正则**。
反射（`CsvDefinitionMapper`）只在**编辑器期**使用，不进运行时热路径；运行时只认资产。

## ADR-009 本地化全量走 key，缺键不回退中文

`LocalizationService`：`HasKey/Get/Format(key, params)/EnumerateKeys/DescribeMissingKeys`。
缺键返回 `[[key]]` 并记警告——**绝不回退显示中文**，否则缺键会被中文掩盖到上线。
键表 `Localization/Tables/localization-zh-Hans.csv` 导入后生成 `Localization/Generated/LocalizationKeys.g.cs` 常量类，代码里写 `LocalizationKeys.Xxx`。
兜底：`HardcodedChineseScanner` + 白名单 `Localization/scan-ignore.txt`，以 Headless 入口在流水线上跑（命中退出码 3）。

## ADR-010 存档版本化，迁移是内部逐版本步进

`Save/SaveData.cs`（`Version/ChapterIndex/MapId/GridX/GridY/RandomSeed/Gold/PlayTimeSeconds/Flag*/心念三轴/队伍/任务/背包/装备分配`）+ `SaveService`：

- `LatestVersion = 3`；`TryLoad` 内调私有 `Migrate(data)` 逐版本步进（v0→按 v1 视之；v1→心念单值拆三轴，负值归 0；v2→装备从扁平列表搬进「成员 × 槽位」并清空旧字段，见 ADR-015）
- `data.Version > LatestVersion` **拒绝加载**，不猜测未来字段
- 写盘用临时文件 + `File.Replace/Move` 原子替换，路径 `saves/slot_XX.json`

**不抽可插拔迁移接口**：当前只有三个版本，接口是为想象中的需求付成本；新增版本时**必须同时**加迁移分支与测试。

## ADR-011 构建与无头入口统一为 executeMethod

- 出包：`SamsaraWest.Editor.BuildPipeline.BuildPipeline.BuildWindows` / `BuildWebGl`（菜单 `SamsaraWest/出包/*`，失败退出码 1，产物落 `Builds/`）
- 无头：`HeadlessTasks.ImportAndValidate`（全量导入 + 校验，0/2）、`ValidateOnly`（0/2）、`ScanHardcodedChinese`（0/3）
- 退出码同时以 `[CI] exit_code=` 写日志，便于流水线抓取
- **批处理串行**：无头 Unity 不可并发跑同一工程（会写坏 `Library`），脚本检测到并发直接拒绝

## ADR-012 生成物一律「内容没变就不落盘」

`SetDirty` + `SaveAssets` 会把内容没变的资产整份重写，mtime 一变 `git status` 就报假改动（`git diff` 却是空的）。
因此清单、数据目录、本地化表、本地化常量类全部按「内容无变化则跳过写盘」实现（范式见 `LocalizationImporter.WriteConstants`）。
**纪律**：新增生成物照此办理，否则每次初始化都会留下假改动。测试套件里的 `ImportAll(force: true)` 会改时间戳，属预期。

不引 ECS、DI 框架、第三方事件库、第三方本地化包；`Narrative` 不接 Ink（属垂直切片阶段），只留目录与 asmdef。

## ADR-014 界面框架定为 uGUI + TextMeshPro

（P8 决策：不在垂直切片期再定，骨架期即收口。）

- 正式界面一律 **uGUI**：`CanvasScaler` 用 Scale With Screen Size，参考分辨率 **1920×1080**（480×270 ×4），一律锚点布局，不写死像素位置。
- 文本一律 **TextMeshPro**，取词走 `LocalizationService`，Prefab 里禁止出现中文（由 `HardcodedChineseScanner` 兜底）。
- 编辑器工具（数据校验窗口等）继续用 **UI Toolkit**：只服务开发期，不进包。
- 8 个装备栏位的展示顺序与文案键统一取 `EquipmentSlots.DisplayOrder` 与 `EquipmentSlots.LocalizationKey`（ADR-015），不在界面里自行排列表。

- **为什么**：uGUI 在 2022.3 的成熟度、图集与九宫格工作流、美术与策划的上手成本都最优；UI Toolkit 的运行时在 2022.3 仍有世界空间、图集与动画的缺口，骨架期押注它等于把风险推迟到内容生产阶段。
- **代价**：两套 UI 技术并存，因此必须守住上文的边界（工具用 UI Toolkit、正式界面用 uGUI）。
- **边界**：Prefab 与场景属内容生产期产物，骨架期只锁约定与栏位口径，不产出界面资产。

## ADR-015 装备 8 槽；存档 v3 用「成员 × 槽位」表达

（P2 决策扩槽，P10 随之迁移；P3 数量口径为 200 件。）

- `EquipmentSlot` 核定为 8 槽：武器 / 副手 / 头盔 / 护甲 / 护腕 / 腿部护具 / 法宝 / 经文。
- **枚举数值只增不改**：`OffHand=5`、`Helmet=6`、`Bracer=7`、`Legging=8` 追加在原 4 项之后——已生成的 SO 资产按整数序列化，改动既有数值会让旧资产串位。
- 展示顺序与文案键**不由枚举数值隐含**，统一取 `EquipmentSlots.DisplayOrder` / `EquipmentSlots.LocalizationKey`；键与文案表的一致性由 `EquipmentSlotTests` 钉住。
- 存档 v3：`List<EquipmentAssignment>`（`CharacterId`/`SlotId`/`ItemId`）取代 v2 的扁平 `EquippedItemIds`。`SlotId` 用字符串名而非枚举，因为 `Save` 不依赖 `Data`（ADR-001）。迁移按队伍顺序把旧装备落到武器栏，随后**清空**旧字段——不留双重真源。
- 校验：`SaveService.Validate` 拦「字段缺失」与「同成员同槽位重复」。

- **为什么**：8 槽是内容侧的真实需求（防具按部位细分）；此刻改的成本只在骨架期，晚改要同时动数据、存档、界面与已产出的 200 件装备。
- **代价**：需 4 类新部位素材；枚举数值与展示顺序不再一致，读代码必须知道去 `EquipmentSlots.DisplayOrder` 取顺序。

## ADR-016 战斗数学是纯函数，掷骰由调用方注入；五行只有一处真源

（2026-09-24 第二轮数值改定：独立暴击 + 相生参与伤害 + 破防比例 5%→2%。口径与校算见《战斗数值 v1》。）

- `DamageCalculator` **不碰 Unity 对象、不读时间、不用全局随机**：伤害是入参与出参的纯函数，公式的九步顺序即实现顺序。
- **暴击掷骰由战斗流程传入**（`ComputeSkillTotal` 收 `IReadOnlyList<float> criticalRolls`，逐段一一对应），掷骰从「战斗」命名随机流取出。因此单测与节奏校算不传掷骰（`DamageInput.NoCritical`）即可拿到确定性结果，而运行期仍是概率行为。
- **五行关系只有一处真源**：`ElementRules.Relate` 返回 `克制 / 借势 / 同属 / 资敌 / 被克 / 无属性`，五类关系把 25 种配对分完；战斗代码禁止自己写元素 switch。
- **克制与暴击是两件事**：`IsCritical` 只表示暴击掷骰命中，`IsElementAdvantage`（读 `ElementRelation`）才表示「这一手元素打对了」。战斗日志可分开显示。
- **数值全部外置**：倍率、护体、破防时长、暴击率等只存在于 `BattleConfig_Default.asset` 与 CSV，不写进 C# 常量；`DefaultAsset_MatchesCodeDefaults` 断言资产与代码默认值一致，避免「测试读默认值、运行期读资产」造成的静默漂移。

- **为什么**：纯函数让「回合数校算」与「单元测试」共用同一条公式，数值改动的影响面可被断言立刻照出来；掷骰注入是纯函数与概率玩法的唯一折中点。
- **代价**：战斗流程必须自己管随机流并负责逐段掷骰；忘记传掷骰会得到「永不暴击」的确定性结果，这是刻意的默认值而非缺陷。

## ADR-017 装备与经文的加成走「进场快照」，聚合只有一处真源

（本条落地即登记：装备与经文的数值此前只是「表里有、能查到」，没有任何运行期消费点。）

- `CharacterStatsResolver.Resolve` 是「角色基础值 + 在身装备 + 经文」的唯一算法：**加算**——不乘、不叠乘、不按品阶缩放；乘区仍归状态与五行关系（ADR-016）。
- **夹下限**口径与 `BattleUnit` 构造一致（生命 1 / 灵力 0 / 攻 0 / 防 0 / 速 1 / 护体 1）：聚合层给主口径，单位构造再兜一次，防止别的入口绕过聚合层造出「速度为 0」的单位。
- 加成在**建单位那一刻**并进 `BattleUnit`，之后是**进场快照**：换装只影响下一场，不会回头改动进行中的战斗。
- 「装备从哪来」与「装备怎么算」分开：`Data` 只认 `LoadoutEntry`（栏位名 + 定义 ID，与存档 `EquipmentAssignment` 同形，见 ADR-015），`Battle` 只认 `IBattleLoadout` 这个最小契约（与 `IBattleInventory` 同一做法），于是 `Battle` 不必反向依赖 `Save`。
- 坏数据**不毁战斗**：栏位名不认、栏位对不上、限定角色不符、定义缺失、非装备种类、重复栏位一律跳过那一件并留下稳定错误码（`LOADOUT_*`），由 `BattleFactory` 在建场时写进战斗日志。
- **暂不生效**（各自要接进伤害公式或回合回路，另行排期）：`breakDamageBonus` 与 `resistElement`（卡在**数值口径**：加成是百分点还是倍率、抗性减伤多少，定下来就能接）；`requiredLevel` 因**角色尚无等级来源**而无处可校验——不臆造等级系统，缺口由一条会随等级系统落地而变红的用例钉住。经文的 `spiritRegenPerTurn` 与 `healthCostPerTurn` 已在 **ADR-018** 接进回合回路；`passiveSkillId` 已在 **ADR-019** 落成「技能挂载」（技能进得来、用得上）；**被动语义已在 ADR-020 落地**——`equipment.csv`／`sutras.csv` 新增 `passiveId` 列指向 `passives.csv`，效果落在它指向的常驻状态上（`statuses.csv` 的 `permanent` 列）。
- 正式流程的接线位置：存档目前没有运行期持有者（`SaveData` 只经由 `SaveService` 读写槽位），因此这一版由诊断层与用例传入；装备界面与「活存档」到位后，传参处即 `BattleFactory.FromEncounter(..., loadout:)`。

- **为什么**：数据齐了不等于玩法通了。装备只「能查到」时，穿上任何一件都不会改变任何数值，而且不报错——静默失效是最难发现的一类缺陷。
- **代价**：定义里的字段与「实际生效的字段」之间暂时有落差，读表的人必须知道上面那份「暂不生效」清单；等级校验要等等级系统。

## ADR-018 经文的每回合效果挂在「自己的回合收尾」

（本条落地即登记：ADR-017 把数值算进了进场快照，但快照里有两个字段的落点不在伤害公式，而在回合回路——经文的 `spiritRegenPerTurn`（每回合回灵）与 `healthCostPerTurn`（苦修失血）。）

- **时机只有一个**：「每回合」= **走完自己一手**，结算点就在 `BattleSession.FinishTurn`，与状态持续伤害、破防计时、冷却递减同一处。ATB 行动值制下速度高的单位一场仗里走的手数更多，于是这两个效果也随速度放大——速度买来的**不只是出手次数**。被控而跳过的那一手照样结算（`BeginNextTurn` 也会走 `FinishTurn`），与状态、冷却的既有口径一致。
- **回灵夹上限**：走 `BattleUnit.RestoreSpirit`，照旧夹在灵力上限内，不会溢出；只对我方有意义（敌人没有灵力机制）。
- **苦修不致死**：生命代价**最多扣到剩 1 点**。代价类经文的设计意图是「扣血换增益」的交易，不是自杀机制——真让它把人扣死，玩家会看到「因为带了一本经文而在自己回合结束时倒下」，而且这一手会被算进我方全灭。这是**刻意的保守口径**，放开之前先拍板（`BattleSutraTurnTests.苦修不会把自己扣死_生命停在下限一` 会先变红）。
- **每回合效果不参与「上限类」的夹下限**：`MaxHealth` 这类数在聚合时被夹到下限 1，而 `HealthCostPerTurn` 是反复发生的量，只保证非负——两者在同一份快照里，但口径不同，`CharacterStatsResolver` 的注释写明了原因。
- **作用面只有我方**：敌人不穿经文，`BattleFactory.CreateUnit` 给敌方阵容传 0；清单里误写给敌人也不生效。

- **为什么**：ADR-017 之后，数值已经在快照里了，但「什么时候用」没定就等于没生效。把时机钉死在回合收尾这一处，整个内核的「每回合」就只剩一个口径，将来加「每 N 回合」类效果时也有现成的挂点。
- **代价**：苦修目前只扣血，其「代价换增益」的交易感全靠经文自身的数值加成承担（如 `SUT_RAGE` 的攻击 +6）；被控跳过的那一手也会付代价，这是口径一致换来的代价，是否合理要等实战手感。

## ADR-019 技能挂载：装备与经文能把技能带进战斗

（本条落地即登记：`equipment.csv` 与 `sutras.csv` 早有 `passiveSkillId` 列，但在本轮之前运行期没有任何地方读它——填了也不会多出一手。）

- **挂载口径**：`passiveSkillId` = 「这件东西让我**多会哪一手**」。聚合层把它并进 `CharacterStatsSnapshot.SkillIds`——**自带技能在前、挂载的按在身清单顺序在后**；重复的只留第一次出现。
- **顺序就是优先级**：规划器的平局判据里有「技能在 `SkillIds` 里更靠前」，界面的按钮顺序也读这一串，于是势均力敌时**自带技能优先被选中**，挂载来的那几手排在其后。
- **一处合成，不再拼第二份**：`BattleFactory.CreateUnit` 直接把 `stats.SkillIds` 交给 `BattleUnit`，战斗侧**不再自己拼一份**「自带 + 挂载」。理由只有一个：清单在哪拼、顺序谁定，必须只有一处答案——两处拼迟早会分叉。
- **坏引用只跳过那一手**：ID 查不到记 `LOADOUT_SKILL_MISSING`；查到了但不是技能（例如误填了敌人的定义 ID）记 `LOADOUT_SKILL_KIND_UNSUPPORTED`。两种都**只跳过那一手**，同一件东西的数值加成照旧生效——坏的是那一手指向，不是整件装备。错误码由 `BattleFactory` 建场时写进战斗日志。
- **重复不算坏数据**：技能清单是**集合语义**——会就是会，两处给同一手不改变任何行为，因此去重但**不报**。只有「查不到」与「种类不对」才留码。
- **挂载不带来特权**：挂上来的技能与自带技能**完全同权**——照样占主行动、吃灵力、进冷却，被拒的理由也同源（`BattleCommandRejection.NotEnoughSpirit`）。`BattleSkillMountTests` 特意钉住这一条：谁哪天给它开了特权（免灵力、不占主行动、跳过冷却），那几条会先红。
- **进场快照**：挂载在建单位那一刻定型；换装只影响下一场，不会把新技能追进进行中的战斗。敌人不穿装备，挂载与敌方阵容无关。
- **字段名与语义的落差（登记在案）**：字段名叫 `passiveSkillId`，定义里的 tooltip 原本写的是「装备后被动生效」——但本工程**没有「被动技能」这种运行期对象**：`skills.csv` 没有「主动／被动」这一列，`SkillDefinition` 也没有对应字段，因此一个技能是主动还是被动**无从判断**。本轮落的是**挂载通路**（技能进得来、用得上），**不是**被动语义。要真做被动，得先定两件事：技能表加「主动／被动」列；被动效果怎么表达（常驻属性修正？触发式？）。两件都不臆造，登记在《待拍板清单》第 7 条。**其中第二件已由 ADR-020 回答**：被动效果**不新造机制**，落在它指向的那条状态上，靠 `statuses.csv` 的 `permanent` 列常驻；剩下「技能表要不要加主动／被动列」仍未拍。

- **为什么**：与 ADR-017、ADR-018 同一个理由——数据齐了不等于玩法通了。这一列此前是「填了也不会多出一手」的静默失效，而静默失效是最难发现的一类缺陷。
- **代价**：读表的人容易把 `passiveSkillId` 理解成「被动效果」，所以字段 tooltip 与聚合层注释都改成了「带进战斗的技能」；真正的被动语义到位之前，这个名字会一直是半个谎。另外挂载只加「能用的技能」，不改变技能本身的消耗与冷却，因此装备带来的招**不会**比自带技能更便宜。

## ADR-020 被动：身份登记在 `passives.csv`，效果落在它指向的那条状态上

（本条落地即登记：ADR-019 打通了 `passiveSkillId`，但装备与经文的 tooltip 写的是「被动生效」，而工程里既没有「被动」这种定义，也没有任何表达「不占行动、常驻生效」的载体。本轮补上这层语义——新增第 18 个定义种类。）

- **被动只登记身份，不登记数值**：`passives.csv` 与其它定义表同构（`id`／`displayNameKey`／`descriptionKey`／`tags`／`version`），唯一与玩法有关的列是 `statusId`——「这条被动的效果载在哪条状态上」。数值一律写在 `statuses.csv`。分工因此只有一句话：**状态回答「会发生什么」，被动回答「这是谁给的」**。
- **ID 与表**：前缀 `PSV_`（`IdRules` 里的第 18 条正则），`DefinitionKind.Passive = 18`，映射写进 `DefinitionImportMap`（`passives` → `PassiveDefinition` → `Passive/`）。于是导入、校验、目录装配、本地化键扫描**全部自动认识它**，没有第二处需要登记的表清单。
- **挂载列**：`equipment.csv` 与 `sutras.csv` 各加一列 `passiveId`，与 ADR-019 的 `passiveSkillId` **并列但互不相干**——同一件东西可以只挂技能、只挂被动，或两头都挂。
- **聚合层只管登记**：`CharacterStatsResolver` 把在身装备与经文的 `passiveId` 并进 `CharacterStatsSnapshot.PassiveIds`（**集合语义**，重复只算一条；顺序按在身清单，只为日志读起来稳定，不含玩法含义）。坏引用只跳过它自己并留码：查不到记 `LOADOUT_PASSIVE_MISSING`，查到了但不是被动记 `LOADOUT_PASSIVE_KIND_UNSUPPORTED`。聚合层**不查 `statusId`、不施加状态**——它连 `StatusDefinition` 都不认识。
- **战斗层做「被动 → 状态」两跳查表**：`BattleFactory.CreateUnit` 在建单位那一刻逐条查表并 `ApplyStatus`。坏引用（被动查不到、承载的状态查不到）只跳过那一条并记 `GameLog.Error`。**施加之后被动就不再参与运行期**：它已经变成身上的一条状态。
- **常驻是状态自己的一列**：`statuses.csv` 新增 `permanent` 列（`StatusDefinition.IsPermanent`）。常驻状态在回合收尾**不递减 `RemainingTurns`、不到期、不进到期回收**，但**每回合量照旧结算**——「每回合回血」这类被动正是靠后半句成立。常驻是一个**不递减的数**，不是一个很大的数。
- **与别的状态完全同权**：被动挂上来的状态进单位的状态清单、参与修正聚合、写进日志与界面状态条，将来任何「按清单挑一条摘掉」的机制也照样认得它。今天的祛毒（`RemoveDebuffs`）只摘负面，因此摘不走增益类被动——这是**同权的结果，不是给被动的特权**。
- **只作用携带者本人**：不广播队友，也不碰敌人。被动不是光环。
- **归位的顺序契约**：被动必须在 `BattleUnit.PrepareForBattle()`（满血满灵、无状态、无冷却）**之后**施加，因为归位会清空状态清单。于是 `BattleSession` **不再自己跑一遍归位**：归位随「建单位那一刻」一次做完，顺序写死在那里。谁改回「先挂被动、再归位」，`BattlePassiveTests` 会先红。
- **界面不画到期日**：常驻状态在状态条上**不显示剩余回合数**（写个数字只会让人以为它要到期），由 `BattleStatusChip.IsPermanent` 转达。
- **为什么**：要么另造一套与状态平行的「常驻修正」机制（第二份修正聚合、第二套回合结算、两处都要维护），要么承认「常驻状态」本来就够用。选后者只有一个理由：修正聚合、每回合结算、时长与叠层规则状态机制已经全有，缺的只是「不到期」这一列。
- **代价**：被动**没有独立的数值表达**，读表的人必须两跳（被动 → 状态）才看得到效果，所以 `passives.csv` 的注释与 `PassiveDefinition` 的 tooltip 都把这句话写在了最显眼处。另外状态实例**不记「是谁给的」**，因此「驱散增益」「按来源解除被动」这类机制今天做不了——要做就得在状态上补一层来源标记，登记在《待拍板清单》第 8 条。

## ADR-021 探索运行时：走格、交互、掷遭遇；接线留在组合根

（本条落地即登记：`Exploration/` 此前只有空 asmdef 与接口契约，是 `待拍板清单` 多轮「仍未做」里的一条。本轮把运行期填上——**数据表一行没改**，只消费已有的 `maps.csv` 与 `interactables.csv`。）

- **依赖方向是这条 ADR 的主语**：`Exploration` 只依赖 Core + Data，它读 `MapDefinition` 与 `InteractableDefinition`、发事件，但**不认识** `IBattleService`、场景与界面。于是 `Flow` 的引用清单同步加上 `SamsaraWest.Exploration`（`ProjectSkeletonTests` 锁住），因为组合根要替「遇敌 → 开战」接线——否则探索就得引用战斗，模块边界会从编译期约束退化成一句口号。
- **服务与会话分工同 `Battle`**：`IExplorationService` 长期存活，只管「开一次 / 记住当前这次」，换图丢会话；`ExplorationSession` 有始有终，只做三件事——走一格、交互一次、掷一次遭遇，然后把结果发成事件。
- **走格顺序是固定的**：`TryMove` 先判遭遇挂起、再判越界、再判占格；走成才更新朝向与步数、发 `PlayerMovedEvent`，**最后**才掷遭遇（「这一步先发生，再决定要不要遇敌」）。**撞墙不改朝向**，于是「面朝哪」永远等于「上一次走成的方向」。
- **交互看的是面朝那一格**：交互物占格且不可进入，玩家永远站在它**旁边**，所以「面向」是必要条件。拒绝分四种理由——`NoTarget`（那格确实空着）/ `Hidden`（有物件但条件未满足）/ `RequirementNotMet` / `AlreadyUsed`，外加 `EncounterPending`。拒绝**不发事件**，只返回理由；事件只报告真的发生了的事。一次性交互物**先记账再发事件**，订阅方（开箱、发奖励）不必自己防重入。
- **换图是数据判据，不是类型键**：交互物的 `targetId` 只要是合法地图 ID（`IdRules.IsValidId(DefinitionKind.Map, ...)`），这次交互就额外发一条 `MapChangeRequestedEvent`，由流程侧决定何时真的换。
- **条件走注入的状态源**：`IExplorationStateSource` 是「剧情状态 → 数值」的单向读取口。缺省实现**全读 0**——这是诚实的退化：状态那本账还没人写，带条件的交互物因此按「条件未满足」隐藏，而不是被当成已满足放出来。`RefreshVisibility()` 按新状态重建格，触发点是「条件键变了」那条事件（剧情侧发），所以它自己**不再发事件**，免得一次开门引出两条刷新。
- **遭遇只掷骰与报告，不开战**：走 `RandomStreams.Exploration` 命名流，调战斗数值不会连带改掉路边遇敌的随机序列。`IsSafeZone` 的地图**即便表里填了概率也不掷**——这条比数据校验硬，校验只警告，运行期必须真的不发生。掷中只挂起 `PendingEncounterId` 并发 `EncounterTriggeredEvent`；挂起期间移动与交互都被拒（`MoveRejection.EncounterPending`），否则玩家连点两下会连开两场战斗。了结靠 `ResolveEncounter()`。
- **接线落在 `Flow/ExplorationBattleLink`**：整条链只有它同时认识探索与战斗。遇敌 → 查遭遇定义 → 取默认队伍（`BattleFactory.DefaultParty`，骨架期的口径）→ `FromEncounter` + `Validate` → `IBattleService.StartBattle`；战斗结束（`BattleEndedEvent`）→ `ExplorationSession.ResolveEncounter()`，漏了这一步玩家在原地一步都走不动。**遭遇当场失效就不开战、也不了结**：查不到定义、队伍为空、入场清单不合法时记错误日志并留着那次遭遇（`IgnoredEncounters` 计数），玩家能看见「这里卡住了」，而不是带着一个静默消失的遇敌继续走。
- **引导期顺序**：`GameBootstrap` 在 `Battle` 之后装 `Exploration`（两者都要读 Data），**最后**建接线（它要同时拿到两个服务）；`OnDestroy` 里先 `Dispose()` 掉接线再清服务。`Dispose` 幂等。**后来者照此办理**：`NarrativeStateLink`（ADR-023）与 `MapChangeLink`（ADR-024）都排在这一段，都是「模块装完再连线」。
- **为什么**：走格、交互、遇敌是三种不同的节奏问题，但它们的共同前提是「地图数据怎么读、随机怎么可复现」——这两件事 Core 与 Data 已经回答完了。所以这一轮不新造机制，只是把已有契约拼成一条能被测试钉住的链。
- **代价**：骨架期只有服务与会话，**没有可玩入口**——没有场景、没有渲染、没有输入绑定，测试是唯一的使用者；「探索可玩」不成立。剧情状态源还没人写，因此所有带条件的交互物现在都隐藏（诚实地退化成「看不见」），且状态变更要人手调 `RefreshVisibility()`。另外 `MapDefinition` 的场地规则与「选择／支线依赖」类触发条件**仍然是未决**（见《未决事项》第 5 条），本轮只支持「状态键 + 运算符 + 数值」这一种条件。

## ADR-022 探索的可玩入口：界面层自挂的诊断面板；UI 允许读玩法模块

（本条落地即登记：ADR-021 的成本栏写着「**没有可玩入口**——没有场景、没有渲染、没有输入绑定，测试是唯一的使用者；『探索可玩』不成立」。本轮把那句话里能先做的部分做掉：**走格真的能在游戏里走**。仍然**没有新资产**——0 个 prefab、0 张切片、0 个新场景。）

- **入口不做场景，做自挂**：新增唯一一个 `UI/Runtime/Exploration/ExplorationScreenView`，`RuntimeInitializeOnLoadMethod(AfterSceneLoad)` 自挂（与 `SkeletonBootScreen`、`BattleScreenView` 同一手法）。工程里没有任何流程会在开图时把它带起来，若靠场景接线，漏挂的那天它会**静默缺席**——诊断层宁可自己出现。`Bootstrap.unity` 一个字没改，Build Settings 也一个字没改。
- **渲染不做素材，做字符**：格子图就是 `@ 自己 / * 面朝 / # 交互物 / . 空地` 的行列文本，一格 18px，行序反过来画（内核 Y 向上、屏幕 Y 向下）。ADR-014 定的正式界面（uGUI + TMP）要一套带中文字形的字体资产才显示得了中文，工程里还没有；正式场景、瓦片图、角色图也还没有。**这一层若强依赖它们，就会在素材还没做的现在什么都画不出来，正好失去存在的意义。** 代价是丑，收益是今天就能走。
- **输入不做 `InputActionAsset`，做 IMGUI 事件**：方向键与 WASD 走格、`E`／空格／回车交互、`F4` 进图离图、`F3` 收起，全部读 `Event.current`，与另两层同一取舍（`UnityEngine.Input` 在「仅 Input System」的后端下会直接抛异常）。`Core` 的 `IInputService`（`Gameplay/Move`）**仍未绑定**，`InputService.cs` 里那句「尚未绑定 InputActionAsset（探索阶段接入）」这一轮仍然没兑现——**因为诊断层不是正式输入面**：正式输入要连着正式移动表现（插值、朝向动画、寻路），那时才有唯一的接入点；把诊断层的按键接进去，只会让「谁才是移动的真源」多出一个说不清的地方。键位映射与交互键判定做成公开纯函数（`DirectionOf` / `IsInteractKey`），好让「输入绑定」本身可被断言——IMGUI 事件没法在用例里合成。
- **`UI` 允许依赖玩法模块**：`SamsaraWest.UI.asmdef` 加上 `SamsaraWest.Exploration`（它此前已经引用 `Battle`）。这不是边界松动，而是**原本就该有的对称**：界面是唯一允许往外看的层，要读服务才能把正在发生的事画出来。`ProjectSkeletonTests` 新增 `Ui_MayReadGameplayModules_ButNotFlowOrEditor` 把两头都钉住——**可以读玩法模块，不许碰 `Flow` 与 `Editor`**。不许碰 `Flow` 这条最容易在赶工时被破：界面想「按一下就直接开一场仗」时，最顺手的做法就是去抓组合根，可那样界面就绑死在「谁先装、装到哪一步」上，启动顺序一改就静默失效。
- **它不含探索规则**：能走到哪、能不能交互、遭遇掷没掷中，全是 `ExplorationSession` 说了算。面板只做三件事——转发一个方向、画当前这一手、把内核给的**枚举**转述成文本键。它也**不认识战斗**：遭遇怎么变成一场仗是 `Flow/ExplorationBattleLink` 的事，面板只把 `PendingEncounterId` 如实画出来。
- **两种拒绝的文案口径，故意与战斗层不同**：战斗只转述「玩家改操作能绕开的」理由，因为其余几种界面本该在转发前拦住（按钮置灰）。探索没有按钮可置灰——玩家按的是方向键，拒绝只表现为「人没动」，所以移动的三种拒绝**全部**给文案：按了没反应必须有一行字解释，否则玩家会先怀疑按键丢了，而不是先怀疑墙。**唯一不给文案的是交互的 `Hidden`**：那句话等于替数据宣布「这里有个机关，只是现在看不见」，把 `isHiddenUntilConditionMet` 想藏的意图当场泄掉——看不见就说不知道。
- **快照不等于状态**：文案只在动作后与 0.5s 兜底间隔到点时重建，`OnGUI` 只负责把拼好的字符串与格子画出去。留兜底间隔而不是只按状态键比对，是因为**遭遇是被别人了结的**——战斗结束时 `ExplorationBattleLink` 会调 `ResolveEncounter()`，那一刻面板看不见，只能靠下个间隔把「可以继续走了」画出来。
- **文案一律走文本表**：新增 20 个 `ui.explore.*` 键（`localization-zh-Hans.csv` → `LocalizationKeys.g.cs` → `LocalizationTable_zh-Hans.asset`），界面层不留任何中文字面量。顺带给 `HeadlessTasks` 加了 `ImportLocalization`：只改文案时不该被迫全量重导入数据表，把明明没改的定义资产标脏。
- **为什么**：ADR-021 的延迟成本是「探索不可玩」，而「不可玩」拖得越久，越容易在最后一刻堆出一个没人验证过的大跳跃。先让它在真实的引导装配、真实的数据表、真实的随机流里被走通一小段，是这一轮唯一想买的东西。
- **代价**：这仍然是**诊断层，不是正式探索界面**——字符格子图、按键直接走格、没有移动表现、没有镜头。而且它**只补上了 ADR-021 成本栏三条里的两条**（输入绑定与正式资源都没做）；`MapChangeRequestedEvent` 目前**只被画出来、没有订阅方**（换图接线在 Flow 侧仍未做）。所以口径是：**「探索可玩」成立到「能走、能撞、能触发」为止，不成立到「能看见画面」**。
  **（2026-10-08 补记）**：成本栏里那句「没有订阅方」**已由 ADR-024 消掉**——换图接线落在 `Flow/MapChangeLink`，首章也补上了两扇门，于是它从「一张孤立的地图」变成「能连着走」。仍未做的是**正式场景、瓦片与角色资源**，也就是本条最后那句口径的后半段，至今不成立。

## ADR-023 剧情状态账：一本「状态键 → 整数」的账落在 Narrative；探索靠 Flow 侧接线重建可行格

（本条落地即登记：ADR-021 的成本栏写着「剧情状态源还没人写，因此所有带条件的交互物现在都隐藏（诚实地退化成『看不见』），且状态变更要人手调 `RefreshVisibility()`」。本轮把这两句里的**机制**做掉——账有人写了，条件交互物会当场显隐。）

- **账本落在 `Narrative` 模块**（此前是只有 asmdef 的空壳）：一本「状态键 → 整数」的账，外加心念三轴（`compassion` / `truth` / `freedom`）。它只依赖 Core 与 Data（骨架测试锁住），事件总线是**软依赖**——没有总线时账本照样能写能读，只是不通知。
- **数据层的契约早就写好了，本轮只是把它实现出来**：`quests.csv` 的目标键（`objectiveStateKeys`）、`dialogues.csv` 的进入条件与写入（`requiredStateKey` / `setsStateKeys`）、`endingconditions.csv` 的判据（`requiredStateKeys` + 三条 `min*`）、以及探索里「条件未满足就隐藏」的交互物，**用的是同一套语言**，所以共读同一本账。`SaveData` 也早就留了 `FlagKeys` / `FlagValues` 与三轴字段——但本轮**没有**接线存档（见代价）。
- **谁写**：公开的 `SetValue` / `AdjustKarma`。数据表里心念从不出现在 `setsStateKeys` / `objectiveStateKeys` 里，只以 `karmaChannel` + `karmaDelta` 的形式**累加**，所以心念**只能**走 `AdjustKarma`；往 `karma.*` 键上写值会被记日志并忽略，免得把累加值悄悄换成赋值。
- **反过来，读口认得 `karma.*`**：`IdRules.IsValidStateKey` 允许这个前缀，于是**理论上**有人会把 `karma.compassion` 填进交互物的 `requiredStateKey`（「慈悲 ≥ 30 才开的门」）。若读口一律返回 0，那扇门会永远打不开，而且看不出为什么——所以 `GetValue` 对这三个键做映射，**读统一、写分开**。
- **什么才算变化**：值真的变了才发事件（同一个键写成同一个数不发）。探索侧靠这条事件重建可行格；重复发会让一次开门引出两条刷新，而且日志里看不出哪次是真变化。写回 0 等于抹掉那条记录，快照里不留没用的 0。
- **坏键进不来**：不符合 `flag./relation./karma./ending.` 规则的键记错误并忽略，日志里带上那个键。账本是全局的，一个拼错的键若静默生效，排查成本极高——这是最便宜的防线。
- **探索怎么读到它**：中间隔一层适配器 `Flow/NarrativeStateSourceAdapter`。`Narrative` 不许认识 `Exploration`（骨架测试锁住），`Exploration` 也不认识 `Narrative`；两边都认识的地方是组合根（ADR-021 的同一条理由）。适配器只转一个 `GetValue`，探索因此看不到账本还有心念、快照这些别的东西。**注意事件不随之提升到 Core**：今天读这本账的只有探索，而**听**状态变化的是「探索重建格」与「界面重画」——后者的诊断面板本来就靠 0.5s 兜底间隔重画，不必订阅，所以跨模块订阅方实际上只有一条线，把它放在组合根最省。
- **「状态变了 → 重建可行格」的接线落在 `Flow/NarrativeStateLink`**：与 `ExplorationBattleLink` 同一种写法。**两条事件都听**（`flag.*` 与 `karma.*` 都可能出现在条件键里）。不在图上时什么都不做——账本可以在进图前就被改，而 `EnterMap` 那一刻本来就按当前账本建格，不必补。
- **为什么**：条件交互物、任务、对话、结局**共用同一本账**，而账本是四者里唯一「谁都能写、谁都能读」的东西。先有账，后面三样才有东西可读。这一轮买的就是**机制闭环**：账能写、读得通、变了会通知、探索当场重建。
- **代价**：**内容写入者还没有**——对话运行时与任务系统都没做，所以没有任何真实玩法会把键置起来解开门。本轮的证据是测试与诊断层（`NarrativeStateLinkTests` 用真数据、真装配证明「写一个键，藏在首章小镇图里的宝箱当场现身」），**不是**一段可玩的剧情。账本**不进存档**：`SaveData` 的字段留着但没人搬，重启即清零——与 `Battle` 的服务同一种期别。心念**不做上下界夹取**（数据层也没有上下界），先如实记录，等结局判定的口径拍板后再决定要不要夹。`interactables.csv` 仍然没有「交互后写状态」的列，所以**扩结构依旧是未决**（见《未决事项》第 5 条），本轮同样**一行数据都没改**。

## ADR-024 换图接线：探索只发出请求，换不换、落在哪由 Flow 定

（本条落地即登记：ADR-022 的成本栏写着「`MapChangeRequestedEvent` 目前**只被画出来、没有订阅方**（换图接线在 Flow 侧仍未做）」。本轮把那根断线接上，并补上首章缺的门。）

- **换图落在组合根**：新增 `Flow/MapChangeLink`，订阅 `MapChangeRequestedEvent`。探索只发请求、不换图（它不认识场景与流程，ADR-021 的那条边界），所以「谁来加载、落在哪」只能落在两边都认识的地方。写法与 `ExplorationBattleLink`、`NarrativeStateLink` 同一种。
- **事件为此扩了一个字段**：`MapChangeRequestedEvent` 新增 `Position`（这扇门在**来源图**上的格子）。落点口径是「目标图里离这扇门最近的可行走格」，不知道门在哪就算不出来——发事件的一方知道而订阅方不知道，那就该由发的一方带上。**只扩事件载荷，不扩数据表**。
- **落点口径**：把门的坐标拿到目标图上，先夹进边界；夹过的那格若可走就用它，不可走则按切比雪夫环由内向外找第一格可走的（`ExplorationGrid.NearestWalkable`）。环内顺序固定——先四个正方向（上 → 右 → 下 → 左），再扫环上其余格。**先正方向是因为「站在门正上方」比「站在门口斜角」更像玩家预期**；顺序固定是因为落点要可复现、将来要能写进存档。整张图没有可走格时记错误日志并退回夹过的锚点——退回原点会让「这张图坏了」看起来像「落点在原点」。
- **服务上多一条进图路径**：`IExplorationService.EnterMapNear`。它与 `EnterMap` 共用同一个壳，差别只有「落点算不算」。**读档恢复仍然走 `EnterMap`**：存档里的坐标是玩家自己走出来的，越界或被占说明数据坏了，那时该留下痕迹而不是悄悄替玩家挪个地方——两条路径的分歧正是本条想固定的东西。
- **先验证再离图**：目标图不在定义目录里时**不动当前会话**，只记一次忽略。先离图再发现目标查不到，玩家就会掉进「哪张图都不在」的状态，那比留在原地并明确记一条错误难查得多。门指向自己所在的图同样忽略（等于让玩家原地卡一次读图）。
- **数据上补了两扇门**：首章此前**一扇门都没有**——`interactables.csv` 那三条交互物分别指向对话、查看、开箱，没有任何 `targetId` 指向地图，所以这条链在真实数据下永远不会触发，只有测试在手工造。本轮补上 `INT_CH01_004_ROAD_GATE`（山道图 (18,6) → 小镇图）与 `INT_CH01_005_TOWN_GATE`（小镇图 (15,5) → 山道图），外加 `ui.prompt.enter` 与四条文案。**新增的是行，不是列**：`interactables.csv` 的列一个没动。
- **两扇门的位置是对着选的**：小镇图比山道图小（16×10 对 20×12），(18,6) 会越界，夹回来是 (15,6)——正好落在回程门 (15,5) 的正南面，进门一步就能看见回去的路。这不是巧合，是**先挑落点、再倒推门位**：落下就被丢到地图另一头，是最容易让人以为「走错了」的那种体验。
- **为什么**：ADR-022 的成本栏里「没有订阅方」意味着首章只能在一张孤立的地图上走——门点了什么都不会发生。这是探索这条线上最后一根断线，接上之后首章才第一次**能连着走**。
- **代价**：进门后的**朝向是写死的南向**——`interactables.csv` 没有「出口朝向」这一列，而「进门朝哪」本质上是场地规则（未决第 5 条）。另外一次性交互物的「用过了」**记在会话上，换图即丢**——出门再回来，开过的箱子这类东西会复活；它该记进剧情账本（ADR-023），等账本进存档时一并处理，本轮不偷偷兜底。诊断面板在换图后仍会显示上一句「前往 CH01_MAP02。」，读起来略啰嗦（状态行已经报出了新图），等正式过场（淡出／加载）到位时一并收拾。最后，**换图发生在事件派发途中**——`TryInteract` 在发出事件之后不再读会话自身状态，所以今天是安全的；这条写进了 `MapChangeLink` 的注释，改那个方法时要一并考虑。

## ADR-025 存档接线：搬运落在组合根，账本整本进出

（本条落地即登记：ADR-023 与 ADR-024 的成本栏都钉着同一句「账本**不进存档**——`SaveData` 字段留着但没人搬，重启即清零」。本轮把那句话兑掉。）

- **接口在 `Save`、实现在 `Flow`**：新增 `Save/Runtime/ISaveCoordinator.cs`（契约：`Capture` / `Apply` / `SaveToSlot` / `LoadFromSlot`）与 `Flow/Runtime/SaveCoordinator.cs`（实现）。**为什么不把实现写进 `Save`**：搬运要同时认识探索（人站在哪张图哪一格）、剧情（那本账）与随机（母种子），而 `Save` 只依赖 `Core`（ADR-001，`ProjectSkeletonTests` 锁住）。这是依赖倒置——下层给契约、上层给实现，而不是让 `Save` 反向去认识玩法。
- **界面认的是那个接口**：`UI` **不许依赖 `Flow`**（同一条骨架测试锁住），而「按一下存、按一下读」总得有人接。于是 `UI` 的 asmdef 新增对 `SamsaraWest.Save` 的引用，面板只认 `ISaveCoordinator`——它知道「世界上有存档这件事」，不知道是谁、按什么顺序把这套服务装起来的。**这是本轮唯一一处模块依赖变动**，已写进 `ProjectSkeletonTests` 的断言。
- **账本整本进出，不逐键搬**：`IStoryState` 新增 `Values` 快照与 `Restore(values, compassion, truth, freedom)`。读档是「换成另一份状态」，不是「在当前状态上叠加」——上一局留下的键若跟着过来，只有玩家读档之后才会发现。`Restore` 的过滤口径与 `SetValue` 一致：坏键跳过并记错误、`karma.*` 跳过并警告（心念只从三个轴字段恢复）、值为 0 的键不留空记录。**不做上下界夹取**，与 ADR-023 同一条。
- **为此新增一条事件**：`StoryStateRestoredEvent(FlagCount, Compassion, Truth, Freedom)`。逐键发 `StoryStateChangedEvent` 一次几百条不现实——`NarrativeStateLink` 会把可行格重建几百遍。于是 `NarrativeStateLink` 从听两条变成**听三条**（`flag.*`、`karma.*`、整本换掉）。
- **采集哪几组字段**：地图 + 坐标、主种子、账本、心念三轴。**没进过图时 `MapId` 留空、坐标归零**——`(0,0)` 会被读成「第一张图的左上角」，两者必须分得开。键按 `StringComparer.Ordinal` 排过序：字典的遍历顺序不保证，而「同一份状态两次采集得到同样的键序」是存档最便宜的回归防线。
- **两处顺序是有意的**：**先校验、再动状态**（目标图查不到就把整份档退回去，免得留下「账本已经换了、人还站在旧图上」的半截状态）；**先复位母种子、再进图**（探索流是在进图那一刻取的，晚一步复位，这一次进图就落在旧种子的序列上了）。
- **读档恢复位置走 `EnterMap`，不是 `EnterMapNear`**：存档里的坐标是玩家自己走出来的，越界或被占说明数据坏了，那时该留下痕迹而不是悄悄替玩家挪个地方（ADR-024 已经为这条分歧埋好了两条路径）。
- **`Capture` 出来的快照要盖版本号**：`Validate` 要求版本在支持范围内，而内存里的快照不带版本号——与 `TrySave` 同一处境，所以由存档服务盖上 `CurrentVersion`。不盖的话，`Apply` 连自己刚采集的档都会拒收，只有「已经落过一次盘」的档才进得来。
- **「用过了」一并进账**：ADR-024 的成本栏写着「一次性交互物的用过了记在会话上，换图即丢——出门再回来，开过的箱子会复活；它该记进剧情账本，等账本进存档时一并处理」。本轮就是那个时候。键的约定在 `Exploration/InteractableFlags`（`flag.interact.<小写交互物 ID>`）；**写**的一侧是新接线 `Flow/InteractionFlagLink`（只听 `OneShot`——可重复触发的查看、对话不记，记下来会让第二次交互被当成「已用过」而拒掉），**读**的一侧是 `ExplorationSession.HasUsed` 自己往 `IExplorationStateSource` 问一句。所以这条线是**单向的（只写不读）**：读档时账本整本灌回来，下次进图的判定自然就对了。
- **诊断入口**：新增 `UI/Runtime/Save/SaveScreenView`（`F5` 存、`F9` 读、`F3` 收起，固定槽位 1），画在**左下角**——左上角已经被探索面板占着，两个诊断层叠在一起会互相遮住，而它们要同时看得见才核对得动。文案全走文本表（新增 8 条 `ui.save.*`），本层一个中文字面量都没有。
- **为什么**：这一轮买的是**跨重启**。此前账本、位置与随机种子全在内存里，重启即清零；接上之后「存一次、关掉、再开、读回来」这条路才第一次真的通。
- **代价**：**诊断入口不是正式存档菜单**，只有一个槽位（`SaveScreenView.DiagnosticSlot` 是常量，正式菜单到位时该退休）。`Capture` **只搬它认识的那几组字段**——装备、经文、背包、货币、进度统统没进档：那几块还没有运行期真源，这里替它们编不出东西。**负心念现在存不了档**：`SaveService.Validate` 拒绝负的心念值，而账本不夹取，所以「心念能减」这条玩法一旦成立，存盘就会整体失败——这是刻意留下的摩擦，提醒心念是否允许为负、上下界怎么夹还没拍板。最后，`Apply` 已经灌回账本与种子、`EnterMap` 才失败时只记一条错误并返回 `false`、不假装成功（这条路径只有「查表时还认得、建会话时又不认了」才走得到）。
  **（2026-10-08 补记）**：上面那句「装备、经文、背包、货币、进度统统没进档」里的**背包与货币已经兑掉**——经济模块落地（ADR-027）之后，`Capture` / `Apply` 多搬了两组字段（`SaveData.Gold` 与 `InventoryItemIds/Counts`），它们第一次有了运行期真源。**装备、经文与进度仍未进档**。

## ADR-026 战果回写：结局记进剧情账本，归因靠事件自带的遭遇 ID

（本条落地即登记：《战斗内核 v1》第 11.1 节第 7 条钉着「**仍缺**……以及**战后结算与剧情回写**（胜负奖励、剧情分支）」，而 `BattleModule.EndBattle()` 的注释里早就留了缝——「战后结算完成、进入下一段剧情时」才该丢掉会话。本轮把「剧情回写」这半句里的**机制**做掉：一场战斗打完之后，结局不再随会话消失。）

- **键约定在 `Flow/BattleFlags`**：形如 `flag.battle.<小写遭遇 ID>.won`，一个结局写一个键、值为 1——与 ADR-025 的 `flag.interact.<交互物>` 同一种口径，账本记的是「这件事发生过」，不是「它现在的状态码」。四种结局各有一个词：`won` / `lost` / `fled` / `retreated`。**尤其是剧情撤退**：已拍板口径是「不算失败、回到剧情前的节点」，所以它写 `retreated` 而**绝不**写 `lost`——把撤退记成战败，会让剧本里「输过一次」「打赢过」这类条件判错，而且错得很安静（这条口径原本只写在 `BattleOutcome.ForcedRetreat` 的备注里，本轮第一次落到流程侧）。
- **先补齐事件的不对称**：`BattleEndedEvent` 原本只有 `Outcome / Rounds / ActionCount`，而 `BattleStartedEvent` 带 `EncounterId`——开打知道是哪一场、打完不知道。归因信息缺了这一块，就只能让组合根自己去猜（比如记住最近一次开打是谁），那是把状态塞回不该有状态的地方。所以本轮给 `BattleEndedEvent` 补上 `EncounterId`（与开打事件对称），**没有遭遇 ID 时为空串**，明确表示「无法归因」而不是臆造一个。
- **写的一侧是新接线 `Flow/BattleStoryLink`**：订阅 `BattleEndedEvent`，按上面四个词往账本写。战斗内核**不认识账本**（连 `Narrative` 都不引用）、账本也**不认识战斗**，两边都认识的地方只有组合根——所以这条订阅落在 `Flow/`，与 `ExplorationBattleLink` / `NarrativeStateLink` / `MapChangeLink` / `InteractionFlagLink` 同一种写法。它**只写不读**：读它的是内容表里的条件（数据，不是代码），以及将来的对话／任务。
- **不记的三种情形**：遭遇 ID 为空（手工构造的战斗，没法归因）记 `UnattributedOutcomes` 并警告；结局不是收场（`Ongoing` 或未知值）记 `UnrecognisedOutcomes` 并报错；键在账本里已经有值则**跳过**（同一场在别的会话里打过，或存档刚灌回来）——`OutcomesRecorded` / `UnattributedOutcomes` / `UnrecognisedOutcomes` 三个计数供诊断与测试。
- **刻意不丢战斗会话**：`BattleStoryLink` **不**调 `IBattleService.EndBattle()`。内核注释写明那是「战后结算完成、进入下一段剧情时」的事，而现在还没有「下一段剧情」；`BattleScreenView` 还在每帧读 `Current` 显示结局，提前丢掉会让玩家看不到自己是怎么赢的。
- **为什么**：这一轮买的是**战果不再蒸发**。此前「打赢了」只活在内存里那场会话中，出战斗就没了；接上之后，「战斗 → 剧情状态 → 条件交互物显隐 → 存档携带」这条链**第一次闭环**——打赢某场 Boss 就能解锁一扇门，而且这个解锁跟着存档走（ADR-025 的账本整本进出）。
- **代价**：**只记结局，不记奖励**——掉什么、给多少钱属于战利品与经济，那两块还没有运行期真源，这一层**不发明数值**，需要奖励时由内容侧去读这个键。**剧情分支没做**——没有 Ink，键先备着。另外，键一旦落进存档就是**存量数据的契约**：将来改词或改大小写口径，就是一次存档迁移的事（见 ADR-007 那条迁移纪律）。最后，**战斗界面与场景仍未做**（全项目 0 个 prefab），本轮的成果要在测试与日志里看。
  **（2026-10-08 补记）**：上面那句「只记结局，不记奖励」里的**奖励已由 ADR-027 补齐**——发**东西**的是新接线 `Flow/LootBattleLink`，本线继续只记**事实**。两条线分开的理由（失败方式不同）见 ADR-027。

## ADR-027 经济：钱袋与背包是独立模块，战利品结算落在组合根

（本条落地即登记：ADR-026 的成本栏钉着「**只记结局，不记奖励**——掉什么、给多少钱属于战利品与经济，那两块还没有运行期真源」，ADR-025 的成本栏钉着「背包、货币……统统没进档」，而《战斗内核 v1》第 11.1 节第 7 条也一直记着「战后结算」未做。本轮把这几句一起兑掉。）

- **接口与实现都在 `Economy`**：新增 `Economy/Runtime/IEconomyService.cs`（`Gold`、`AddGold` / `TrySpendGold`、`CountOf` / `AddItem` / `TryRemoveItem`、按 ID 排序的 `Items` 快照、`Restore` / `Clear`）与内存实现 `EconomyService`。它**只依赖 `Core` 与 `Data`**，不认识战斗、场景与存档——与 `Exploration`、`Narrative` 同一种站位。
- **不落盘**：`EconomyService` 不碰磁盘。落盘是 `Save` 的事、搬运是组合根的事，正是 ADR-025 的手法。
- **结算是一个纯函数**：`Economy/Runtime/LootResolver.cs`，`Resolve(encounter, definitions, stream, report) → BattleSpoils`。给定同样的遭遇、目录与随机流必然得到同样的战利品：不碰服务注册表、不写日志、不改状态。**掷骰顺序定死**——按 `enemyIds` 出现顺序逐只敌人结算，每只先「必掉」再按权重抽 `dropRolls` 次；顺序一变，同一种子掷出的东西就变了。
- **两套金钱来源并存**：敌人定义的 `goldReward`（确定值）与掉落表的 `goldMin` / `goldMax`（掷出来的）。这是《战斗数值 v1》既有的口径，本轮**只读、不改表**，也没替它们合并成一种。
- **经验算出来但无处安放**：`BattleSpoils.Experience` 把敌人的 `experienceReward` 一并带出来，但**没有消费者**——等级系统不存在。留着是为了让这个缺口**看得见**：它在日志里被念一遍，而不是在某处被悄悄丢掉，等到做成长模块时才发现「经验到底该给多少」已经没人答得上来。
- **战利品走独立随机流**（`RandomStreams.Loot`）：改掉落表不会挪动战斗的判定序列，反之亦然（ADR-005 的流分离）。**代价**——读档只灌母种子（ADR-025），掉落流从头开始，所以奖励是**可复现的、但不是「接着上次继续」**；要精确续流得把 `SnapshotAll` 一并搬进存档，那是另一件事。
- **接线落在组合根**：新增 `Flow/LootBattleLink`，与 `BattleStoryLink` 读同一个 `BattleEndedEvent`，但**只有 `PlayerVictory` 会结算**——战败、逃跑与剧情撤退（`ForcedRetreat`）都不发东西（《战斗内核 v1》第 11.2 节的口径，这条线第一次真的落地）。撤退也发奖励的话，「打不过就退」会比打赢更划算。
- **为什么和战果回写分成两条线**：那条线记**事实**（这一场赢了），这条线发**东西**（给了多少钱与物）。分开的理由是**失败方式不同**——账本键写重了只是记错一件事，战利品发重了是玩家凭空多拿到钱。
- **不设「一个遭遇只结算一次」**：探索的遭遇本来就随机可重复触发，重复打赢拿重复掉落是这类游戏的常态；一次性奖励属于任务奖励，不是战利品。**真正的一次性由内核保证**——`BattleSession` 的结局只有一个出口且幂等，同一场仗不会广播两次结局，也就不会发两遍东西。
- **不结算的三种情形各记各的数**：收场不是胜利 → `SkippedOutcomes`；没有遭遇 ID（手工构造的战斗，无从归因）→ `UnattributedOutcomes` 并警告；遭遇查不到、或结算途中撞上数据问题 → `UnresolvedSpoils` 并报错。**坏数据只跳那一条**——某只敌人或它的掉落表查不到，其余照常发放，不让一处配置错误把整场结算炸掉（同 `BattleFactory` 对在身装备的处理）。`Settlements` / `GoldSettled` / `ItemsSettled` 供诊断与测试。
- **战斗第一次有了真背包**：内核的 `IBattleInventory` 在正式流程里此前一直是 `null`，道具指令问谁都要不到东西。新增 `Flow/VaultBattleInventory` 把「还有几个、扣掉一个」转述给钱袋与背包。它是**两边的翻译**而非任何一边的依赖——战斗内核不认识经济（连 `Economy` 都不引用），经济也不认识战斗（连 `Battle` 都不引用），两边都认识的只有组合根，手法与 `NarrativeStateSourceAdapter` 完全一样。
- **存档多搬两组字段**：`SaveCoordinator` 的 `Capture` / `Apply` 现在带上 `SaveData.Gold` 与 `InventoryItemIds/Counts`，`ISaveCoordinator` 的注释同步改了口径。**没有加字段，只是把它们填上**——这两个字段从存档 v1 就在，一直没人读写（ADR-025 已补记）。
- **为什么**：这一轮买的是**打赢之后真的落到玩家身上**。此前掉什么、给多少钱只活在内存里那场会话中，出战斗就没了；接上之后「战斗 → 战利品 → 钱袋与背包 → 存档」第一次闭环，而且战斗里也能真的用掉一件掉落。
- **代价**：**钱与经验只进不出**——没有商店、没有消费端，`TrySpendGold` 与 `TryRemoveItem` 目前只有战斗背包在调；经验更是完全没有消费者。**看不见**——没有钱袋界面，全项目仍 0 个 prefab，本轮的成果要在测试与日志里看。**结算读的是当时的目录**：`LootResolver` 拿 `IDefinitionRegistry` 现查、不注入快照，所以调完平衡重启之前，结算口径就是目录当时的样子。**装备、经文与进度仍未进档**（ADR-025 补记）。最后，**稀有度、保底与一次性掉落的归因都没做**——同一件东西从谁身上掉的，现在只看得出件数，没有来源标记。

## ADR-028 在身清单：装备与经文有了第一个运行期真源，整本进出存档

（本条落地即登记：ADR-017 定下了「装备与经文怎么算」，ADR-019 把它们带来的技能挂上去，ADR-020 把被动落在常驻状态上——但一直没人回答「**谁身上穿了什么**」。`IBattleLoadout` 是有的，正式流程里却恒传 `null`（ADR-017 代价栏：「存档目前没有运行期持有者，因此这一版由诊断层与用例传入」）；`SaveData.Equipment`（`EquipmentAssignment`，v3 就留好，ADR-015）也一直没人读写（ADR-025／027 补记里那句「**装备、经文与进度仍未进档**」）。本轮把这两句一起兑掉。）

- **接口与实现都在 `Equipment`**：新增 `Equipment/Runtime/{EquippedItem,IEquipmentService,EquipmentService,EquipmentModule}.cs`。它**只依赖 `Core` 与 `Data`**，不认识战斗、背包、场景与存档——与 `Economy`、`Exploration`、`Narrative` 同一种站位。
- **簿子的形状就是「成员 × 栏位 → 定义 ID」**：`EquippedItem` 是个小结构体（`CharacterId` / `SlotId` / `ItemId`），`SlotId` 用字符串名（与 `EquipmentSlot` 的名称、与 `Save` 的 `EquipmentAssignment` 同形），不把枚举塞进契约里。`Snapshot` 按「先成员 ID、再栏位展示顺序（`EquipmentSlot` 枚举序）」排好，理由与 ADR-027 的背包快照一致——**同一身装备两次采集必须得到同样的排列**，否则会写出两份「内容相同、顺序不同」的档。
- **读档是「换一本簿子」，不是往上叠**：`Restore` 先清空再逐条灌入（`Restore(null)` 等于清空），与状态账、钱袋的搬运口径一样。坏条目**只跳过它自己**（成员查不到、栏位名认不出、定义查不到、限定角色不符、栏位对不上），其余照常读进来——半身装备不该让整份存档读不进来（同 `BattleFactory` 对在身装备的处理）。跳过谁、为什么，由 `EquipmentService` 写 `LogChannel.Equipment` 的错误日志。
- **校验口径只有一处**：`EquipmentSlots.TryParse`（`Data/SharedEnums.cs`）。**这一轮把它上移成了公共口径**——此前 `CharacterStatsResolver` 私有一份 `TryParseSlot`，在身清单若自己再写一份，两处迟早分家，然后出现「画像认得、清单不认得」的同一个栏位名。现在 `CharacterStatsResolver` 改为委托 `EquipmentSlots.TryParse`，进场画像与在身清单共用一份：**严格名字回比**（大小写敏感，`Enum.TryParse` 会认的数字串、逗号组合如 `"Weapon, Armor"` 一律不认），免得「猜一个栏位出来」。
- **它刻意不做的四件事，各有理由与用例钉着**：**不认识背包**（穿上不扣、脱下不还——穿脱与钱物没有连线）；**不校验需求等级**（`requiredLevel` 无处可问：等级系统仍是空壳，硬拦会把需要等级的装备变成永远穿不上的死数据）；**不校验归属**（目录里的装备是按 tier 归并的通用件，「一件东西只有一份」需要一条归属线）；**不管战斗**（清单只是被读的事实，不参与怎么算）。前两件各有一条**会随等级系统／背包接线落地而先变红**的用例钉住缺口，而不是假装它已经做对了。
- **不落盘**：`EquipmentService` 不碰磁盘。落盘是 `Save` 的事、搬运是组合根的事，正是 ADR-025 的手法。`SaveCoordinator` 的 `Capture` / `Apply` 现在带上 `SaveData.Equipment`，**没有加字段，只是把它填上**；`SaveService.Validate` 早就拦「同一成员的同一栏位出现两次」这类档。
- **接线落在组合根，靠一个转述者**：新增 `Flow/EquipmentLoadoutAdapter` 把内核的 `IBattleLoadout` 转述给在身清单——`Battle` 不认识 `Equipment`（连引用都没有），`Equipment` 也不认识 `Battle`，两边都认识的只有组合根，手法与 `VaultBattleInventory`（转经济）、`NarrativeStateSourceAdapter`（转剧情账）完全一样。`ExplorationBattleLink` 因此第一次把**非 null** 的 loadout 传进 `BattleFactory.FromEncounter(..., loadout:)`。
- **为什么**：这一轮买的是**「装备与经文在真流程里第一次真的生效」**。ADR-017～020 把「怎么算」「技能怎么带」「被动怎么落」都定了，但正式流程里 loadout 恒为 `null`，于是这些口径只活在诊断层与用例里；接上之后「穿上 → 数值与技能进战斗 → 随存档进出」第一次闭环。
- **代价**：**没有穿戴界面**（全项目仍 0 个 prefab），穿脱只能在代码与测试里做，`TryEquip` / `TryUnequip` 目前没有界面消费方。**穿上不扣背包**——掉落进背包的是 `ITM_*` 道具，而装备是 `EQP_*`／经文是 `SUT_*`，两条目录今天没有连线，「捡到一件装备就穿上」尚未打通。**等级与归属仍未校验**（见上，各有变红用例钉住）。**战斗仍读当时的目录**——`EquipmentLoadoutAdapter` 现查 `IDefinitionRegistry`、不注入快照，与 `LootResolver` 同一种取舍。最后，**经验与进度仍未进档**（ADR-025 补记未清）。

## ADR-029 剧情节点（对话）运行时：节点由数据串起来，推进器不认识文本

（本条落地即登记：`Narrative` 从 ADR-023 起只有一本状态账；`Data` 侧从第 22 轮起有 `dialogues.csv`，第 23 轮把前山拆成了节点行——但**没有任何东西会推它**，那 19 行字谁也读不到。ADR-017／027／028 那一串「接口是有，正式流程里恒传 `null` / 没人读写」的代价栏，这一轮轮到剧本。）

- **接口与实现都在 `Narrative`**：新增 `Narrative/Runtime/{DialogueTypes,DialogueService}.cs`，事件补进 `NarrativeEvents.cs`。它**只依赖 `Core` 与 `Data`**，不认识界面、本地化与场景——与 `Exploration`、`Economy`、`Equipment` 同一种站位。
- **推进器不产文本，只给「该念哪一个键」**：一段话的行键是 `<前缀>.line.<n>`（说话人是 `<前缀>.line.<n>.who`），前缀由定义的 `displayNameKey` 去掉末尾 `.name` 得到，**拼不出前缀就交空串而不是猜一个键**——让界面把「缺的是哪个键」报出来，而不是悄悄画出一片空白。它**不引用本地化服务**：「该念哪一行」由推进器给，「那一行长什么样」在界面里解析。这样界面仍是唯一认识字的地方，推进器的用例也才能断言键名而不是汉字——拿汉字去测，等于把本地化表也锁进了这一层。
- **后继由条件挑，挑不到就收场**：`nextNodeIds` 登记剧本节点名，逐个看 `requiredStateKey / requiredOperator / requiredValue`，第一个满足的赢。**这是本轮的中心口径**——不是「每段对白都硬接下一段」。
- **新增 `isTerminal` 列**：环境调查类节点（断鼓、血迹、山门）在剧本里是「看完就回到自由探索」。第 23 轮没有这一列，只能把它们串成一条**假的线性链**顶着，于是「调查断鼓」会接着念一段血迹的旁白——**数据说了谎**。加这一列之后，它们能在数据里说「到此为止」。**这是本轮真正的根因修复**，也是第 23 轮「仍未做」里「环境调查节点如何收束」的答案：收束方式由内容写，不由引擎猜。
- **写入只在节点读完时结算**：`setsStateKeys` 与 `karmaChannel` 都在当前节点读完那一刻（`FinishNode`）落进账本，代表「这段播过了」。第一行就记账的话，「走到一半退出」也会被算成读完——而「**问过的问题不再问**」正是靠这个标志位成立的，不是写死的。
- **心念复用账本的通道口径**：`karma.*` 通道经 `KarmaAxes.TryParseChannel` 解析成 `KarmaAxis`，与存档、与画像同一处真源。
- **被拒就说理由，不抛异常**：`TryStart` 返回 `DialogueStartResult`，`Rejection` 分 `UnknownDialogue`（含「这个 `targetId` 指向一张地图」）／`AlreadyActive`／`RequirementNotMet`。玩家对着空气按 E 不该是崩溃，界面也不必回头再问一遍「为什么没开」。
- **两套索引各管各的**：按 ID 直接开（交互物的 `targetId` 指的就是 `DLG_*`）与按剧本节点名挑后继（`InkKnotName`）是两件事。节点名重名时**先登记者赢**并记一条日志——选错了不是「谁赢」的问题，是「接在招呼后面的那段话悄悄换成了另一段」。
- **接线落在组合根**：新增 `Flow/ExplorationDialogueLink`。探索只发 `InteractionTriggeredEvent`（「有人在 20,8 上按了 E，目标是 DLG_CH01_002」），它不许认识 `Narrative`；推进器只会推进它已经开着的那段，也不许认识探索。**判据是数据不是名单**——拿 `targetId` 去对话表问一句「这是不是一条对话」；指向地图（门）或掉落表（箱子）时自然问不出来，于是不必维护一份「哪些交互算对白」的名单。但**类型键要筛一道**（`interact.dialogue` / `interact.examine`），否则每开一次箱就留一条「找不到对话定义」的假警报，把真问题淹掉。
- **换图时由接线收场**：F4 那种「直接切图」的诊断入口在界面里排在模态判定之前（不然就对着一张对白按不动 F4），于是「对白开着一半切了图」这条路真的存在，而推进器**不会自己知道**。接线因此也盯 `MapEnteredEvent`，一到就把开着的对白收掉；收场走「中断」而不是「读到底」——玩家没读完，不该按读完记账（账面写入代表「这段播过了」）。
- **界面是模态的，而且这是唯一挡住方向键的地方**：`ExplorationScreenView` 上加对白块（标题／状态行「节点名 · 第 n/N 行」／说话人／正文），对白开着时方向键不外传、交互键变成「继续」。探索内核不认对白，不会替界面挡住——所以这条判定必须在界面层，且必须**整块吃掉按键**：漏一个键，玩家就能一边看对白一边走动。
- **为什么**：这一轮买的是**前山那 19 行字第一次真的能被读到**。第 23 轮把地图与节点做成了数据，但没有任何东西会推它；接上之后「按 E → 念一行 → 再按 → 念下一行 → 念完回到自由探索」第一次闭环。
- **代价**：**没有 Ink**——节点图今天是「条件 + 后继」的两段式，玩家**没有选择**（剧本里迎客猴的 A/B 选项这一轮登记成了「条件后继」，不是选项）。**没有立绘、没有打字机、没有自动播放、没有历史记录**（全项目仍 0 个 prefab，本轮的成果要在测试与日志里看）。**只有诊断入口**：F4 那张图与探索面板是仅有的可玩面，正式场景与正式界面仍是空白。**离图时对白不会立刻收**（面板离图后不再画对白块，所以看不见），下一次进图必收。**任务系统仍未做**——`Narrative` 责任栏里那句话，这一轮只划掉了前半句。

## ADR-030 Boss 阶段：阈值由数据给，换档与演出由内核串起来

（本条落地即登记：`bossphases.csv` 从第 12 轮起就把四档写好了——阈值 `1 / 0.7 / 0.4 / 0.15`、每档的技能组、三个倍率、入场状态、台词与换曲／推镜头键，定义、导入映射、校验与 4 个 `.asset` 一应俱全；`BENC_CH01_001` 的 `bossPhaseIds` 也填满了四条。**但战斗里没有任何一行代码读它**——截至落地前，混世魔王在实战中只是「一个血厚、会四招的普通敌人」，四档剧本谁也看不到。ADR-017／027／028／029 那一串「接口是有，正式流程里恒传 `null`／没人读写」的代价栏，这一轮轮到阶段表。若不先补这一层，`CH01_MAP05` 的 Boss 战无从谈起。）

- **判定收在一个不认识战斗的类里**：新增 `Battle/Runtime/BossPhaseTrack.cs`，它只回答「该不该进下一档」——给一条生命比例就问得出答案。换档之后发生什么（换技能组、写倍率、挂状态、发事件）全在 `BattleSession` 里。分开的理由是判定这一半要能单独测，不必先把整场战斗推到那个血量上。
- **判定只认「生命比例 ≤ 阈值」这一件事**：比较取 `<=`，于是阶段表把第一档写成 `1.0` 就意味着「开局那一刻命中」。**开场技能组与换档技能组因此走同一条路，没有特例**——不给「第一档」写一段专门的启动代码，那正是上一段那种「数据写了、没人读」的温床。排序按阈值**从高到低**：判定靠「跌破就前进、没跌破就停」一次走完，顺序错了就会在第一档上停死。
- **触发点只有两处，覆盖所有生命变化**：① 一整手技能对全部目标结算完毕之后；② 单位自己回合收尾（持续伤害与苦修结算）之后。第一处刻意**不放在每一段伤害之后**——一次行动是原子单位，该问的是「这一手打完打到哪了」，而不是在一手的多段之间反复横跳。第二处是必须的：Boss 被持续伤害或自己的苦修跌破阈值时，走的不是技能那条路。
- **进度单调，只前进不后退**：就算把 Boss 治回满血也回不到上一档。档位记的是「已经打到哪一步」，不是「现在处于什么状态」；回头重播一遍台词与换曲没有意义。一次重击跨两档时**逐档推进**——中间那一档的入场状态与演出都要发生，不能静悄悄跳到最后一档。
- **换档换的是「这一档会哪几手」的全集，不是补丁**：`skillIds` 整体替换掉单位的技能清单，于是「最后一档只剩压箱底那一手」是数据说了算。**在冷却中的技能不受换档影响**——冷却跟着技能 ID 走、不跟着阶段走，否则每次换档都等于白送一次大招。**敌人表里的 `skillIds` 只在没有阶段表时才算数**：两个真源会互相打架，因此明确排出主次。
- **三个倍率是独立于状态修正的另一个乘区**：状态写「+30%」，阶段写「这一档整体 ×1.25」，`EffectiveAttack = 基础 × (1 + 状态修正) × 阶段倍率`。分区的理由与 ADR-017 同源：它们来自两份表，调档位不该顺带改掉状态表的加成口径。倍率为 1 时算出来的数与这一层落地之前**逐位相同**，所以这是一次纯增量。
- **入场状态走 `statuses.csv`，不是新机制**：阶段表的 `onEnterStatusIds` 指向既有的状态定义，施加路径与技能挂状态、在身装备的被动完全一致，连事件都是同一条 `BattleStatusAppliedEvent`。
- **阶段表按遭遇对齐**：阶段定义的 `encounterId` 与本次战斗的遭遇不一致时**跳过那一条**并记日志。串表是真实会发生的错误，而症状（「Boss 的第三档带着别的遭遇的招」）极难从表现上倒推回数据。
- **事件是「这一档已经落实完毕」的信号**：`BattleBossPhaseChangedEvent` 在技能组、倍率、入场状态都就位之后才发出，并带上 `tauntKey / bgmSwitchKey / cameraCueKey` 三个键。订阅方接到它时重绘一次就够，不必猜还有没有后续；界面认不认识这三个键都不影响内核继续跑。
- **表坏掉就退化，不停战**：查不到定义、类型不对、遭遇串了、入场状态没登记，都只记一条日志并跳过那一条——与在身装备、被动同一条口径。整张表都坏掉时，这一战退化成「Boss 只有单一形态」，而不是打不开。反过来，遭遇配了阶段但敌方**没有**标记为 Boss 的单位时要专门记一条——那是配置错误，不是设计选择。
- **接线落在入场清单**：`BattleSetup` 新增 `bossPhaseIds`，`BattleFactory.FromEncounter` 从遭遇定义接过去。与 `Party` / `Enemies` 同一站位——`BattleSession` 只认这份清单，测试里可以手工拼一档出来，不必先造遭遇资产与四张阶段资产。
- **为什么**：这一轮买的是**四档剧本第一次真的能在战斗里发生**。`bossphases.csv` 在数据层静置了一轮多，阈值、技能、倍率、台词全部待命；接上之后，「打到七成换一副牌、被打疼了挂一层暴走、最后一档只剩一招」第一次闭环。
- **代价**：**没有新的可玩面**——阶段机的成果只在测试与日志里看（全项目仍 0 个 prefab，战斗本身仍无正式界面，阶段事件没有订阅者）。**演出键只是键**：`tauntKey / bgmSwitchKey / cameraCueKey` 由内核发出去，谁都不认，真正的换曲、推镜头、念台词要等界面层与美术层。**只有血量阈值一种触发**：没有「第 N 回合」「被某个技能打中」「队友倒下」这类触发条件，也没有「回到上一档」的表达——位置在 `bossphases.csv` 的既有列里，扩它属于「触发条件／场地规则的表结构」那件事。**阶段表不认识「阶段专属技能」**：换档只能从单位已有的技能全集中收窄，不能凭空给 Boss 加一招只有这一档才会的招——今天得靠把那一招挂在敌人定义的 `skillIds` 里、再由早期档位把它排除在外来间接表达。

## ADR-031 定点遭遇：交互物的目标 ID 指向遭遇时，走上去就开打

（本条落地即登记的缺口：ADR-021 起，探索只有**一条**遇敌路径——每走一步按 `maps.csv` 的 `encounterRate` 掷一次骰子，掷中了打 `encounterTableId` 那一场。剧本里的遭遇却不都是这样来的：「进入魔王洞门前触发 `ENC_CH01_005`」「子时一到，`BENC_CH01_001` 在轮回台等着」，说的都是**走到某处必然打这一场**。上一轮（`CH01_MAP04`）撞上这个缺口时采取的权宜之计是「把 Boss 摆进场地」的反面——把该定点触发的 `ENC_CH01_005` 换成 `0.12` 的随机率顶着；Boss 战则**完全无处安放**，因为把整张图挂上 Boss 的随机遭遇表会让玩家在洞里随便走两步就撞见最终 Boss，而它 `allowFlee = false`、`defeatGameOver = true`。）

- **判据沿用「ID 的形状」，不新造类型键**：交互物的 `targetId` 只要是合法遭遇 ID（`ENC_ / EENC_ / BENC_ / OPT_` + 章节 + 三位序号），这次交互就是一次定点遭遇。这与换图用的是**同一条判据**（ADR-024：`targetId` 是合法地图 ID 就是换图），同源的理由也一样——不维护第二份「哪些交互物算门、哪些算仗」的名单，名单会跟数据表各自漂移。
- **落地位置在 `ExplorationSession.TryInteract`**：换图分支之后加一条并列的分支，发的是**同一条** `EncounterTriggeredEvent`、走的是**同一本**挂起账（`PendingEncounterId`）。于是「挂起之后走不动、不能再交互，直到 `ResolveEncounter` 被调用」这条不变量一个字都不用改，开战也仍然由 Flow 侧的 `ExplorationBattleLink` 决定——探索依旧不认识战斗（ADR-021 的依赖方向不动）。
- **`InteractionResult` 上多两个平行字段**：`RequestsEncounter` 与 `TargetEncounterId`，与既有的 `RequestsMapChange` / `TargetMapId` 成对。界面与测试因此不必要靠再去查一次定义表才知道「刚这一下是不是要开打」。
- **为什么**：这一轮买的是**「定点」这种遭遇第一次真的存在**。有了它，Boss 战才有了落脚处，而不必靠随机率顶替；「走到某处必有一战」也不必再等场地规则的表结构。
- **代价**：**挂起与开战之间没有原子性**。挂起判定只看 ID 形状，不看定义表里有没有这一场；若 `targetId` 写得像遭遇 ID 而目录里查无此遭遇，`ExplorationBattleLink` 会按既有口径忽略掉，而挂起账**没人来清**——玩家会卡在原地走不动（随机遭遇那条路径有同一个风险，只是一直由数据校验器兜着）。今天的口径是「引用由数据校验兜住，运行期不重复兜底」，这条留给「数据校验器的引用完整性」那件事。**依然没有「打过一次就消失」以外的重打口径**（`oneShot` 交互物只管自己的可见与可否再触发，不管战斗结果），也**没有「打输了会怎样」的场地级表达**（Boss 的 `defeatGameOver` 写在遭遇表上，不是写在地图上）。

## ADR-032 渲染层底座：底图与人站在 SpriteRenderer 上画，不引 Tilemap

（本条落地时登记的缺口：ADR-021 起，探索只有**一种**画法——`ExplorationScreenView` 用 IMGUI 把地图打成 ASCII 字符网格。从 ADR-021 到 ADR-031 的每一轮里，这条缺口都在「代价」里记着：全项目 0 个 prefab、0 张美术图在跑，地图再大也只是字符多几列。素材侧这一轮交付了花果山前山 1920×1280 的底图与元素图集，于是「把地图真的画出来」这件事第一次有了落脚处。）

- **选 SpriteRenderer，不选 Tilemap**：Tilemap 的价值几乎全在**编辑器里刷格子**——可今天的地图排版（`maps.csv` 只有尺寸、底图键、原点偏移）根本不在 Unity 里，没有 Tile 资产、没有 Tilemap 组件，也没有任何按格摆放的地形数据。上 Tilemap 等于先造一套用不上的编辑器工作流，再为它维护一份与本就不存在的排版数据同步的资产。SpriteRenderer 用**同一份数据**在运行时摆位置，编辑器侧一点不欠。将来真要 Tilemap，只需换掉 `ExplorationSpriteView` 一层实现——它对上层暴露的面只有「重画一次」（ADR-032 的可替换性就落在这一条上）。
- **导入参数是可复现的代码，不是提交的元数据**：`Assets/_External` 是到 `E:\tx2\素材` 的**目录联接**、不入版本库，所以它的 `.meta`（Sprite 类型、Single 模式、PPU 32、Point 过滤、无 mipmap、不压缩、Clamp）**不能靠提交来保证**——换一台机器、换一个工作区就从零生成。`ExternalSpritePostprocessor` 作为 `AssetPostprocessor` 在导入时把这一串参数按代码统一钉上，`_work / _preview / _src / _base_1x` 这些中间产物目录按路径排除。这也解释了「32 像素」这条链为什么必须写在代码里：PPU 32 ↔ `tilePixelSize` ↔ 相机正交 ↔ 480×270 基线，四者是同一件事的四个说法，任何一处靠人手设都会漂。
- **素材绑定从美术侧的 JSON 自动来，人只列「整图」**：图集 JSON 的帧自带 `spriteKey`（`sprite.int.*`），`SpriteCatalogBuilder` 扫出来直接绑，美术改图集这里跟着变；只有「整张图就是一个精灵」的（底图、立绘）没有帧可依，列在 `sprite-sources.csv` 里由人维护，留空即表示「还在等美术」。产物 `SpriteCatalog.asset` 进版本库——**程序产物入 git 才好 diff、好 Review**，也才好在没有素材的工作区里看出「原本该绑哪些键」。
- **坐标换算只留一份**：`GridGeometry`（格 ↔ 世界）是底图、交互物、角色、相机**共用的唯一口径**，原点在左下、Y 向上。角色站的是格子的**底边中点**而非格中心——立在地上的人站的是地面线，差半格就是陷进地里。这一层单独抽出来，是因为「底图对得上、物件差半格」是最容易发生又最难从画面上倒推回数值的错误。
- **缺素材是常态，而且是**报出来**的常态**：首章只有 CH01_MAP01 交付了底图与元素，其余四张图数据有、素材没有。缺底图时铺一块按网格尺寸的暗色（空白会让人以为渲染层没生效，有边界的暗底能直接告诉你「图是这么大」），缺交互物素材时记进 `MissingKeys` 而**不画占位**——满屏洋红方块比留白更难看。构建器把底图缺口、交互物缺口、待交付分开报，缺口数是**会随美术交付下降的指标**，不是错误。
- **两层叠放靠排序与让位**：精灵层按 Y 排前后（Y 越小越靠前），底图 -1000、缺底图暗色 -900。精灵层一旦有图可画，`ExplorationSpriteView.IsActive` 为真，`ExplorationScreenView` 就把 ASCII 网格缩到 0 并停画——输入、对白、诊断文字仍归界面层，画面归精灵层，同一条信息不许画两遍。
- **相机跟随默认整像素吸附**：像素画里镜头平移一旦插值，相机就落在半个像素上，整屏重采样发糊。`CameraFollowRig` 默认 `_smoothTime = 0`，整格跳动；换图时**显式吸附一次**（跟随器的目标始终是同一条玩家对象，光靠「换目标」换不掉位置，不吸就会从上一张图滑过去，像镜头飞了）。
- **为什么**：这一轮买的是**探索地图第一次是「画」出来的，而不是「打」出来的字符**。ADR-021 起，探索的运行时（走位、交互、换图、定点遭遇）一直是完整的，唯独没有画面；素材一到位，把渲染层立起来就是让前面十一轮的东西第一次有个能看的落点。
- **代价**：**素材还会改**——这一轮只锁「尺寸不变、只改内容」这一条（32 那条链因此不会因换图而漂），但内容一改图集帧坐标就得重绑，所以重建工具是常备工具而非一次性的。**首章仍缺 4 张底图、32 个交互物素材**（构建器如实报出），**角色还是代码生成的占位方块**——角色图集有 4 帧但没有 `spriteKey`，要绑它得先有一张「数据键 → 帧名」的对照表，那是另一件事（三套武器图集、农场元素图集、以及花果山前山元素图集里的装饰帧同样卡在这里，本次构建共报出 117 个无键帧）。**没有 Tilemap 附带的那些东西**：没有自动碰撞体、没有按格物理、没有 Tile 调色板。**遮挡只到排序为止**：人与物走到树后**不会被树挡住**，因为排序只按 Y 一层。**相机没有边界钳制**：图比视口大时能一路走出图外。**换工作区要重跑一次重建工具**把贴图引用接回来（`Assets/_External` 不进库的直接后果）。**这套只在探索画面生效**：战斗、对话、菜单仍是纯逻辑，没有画面。
